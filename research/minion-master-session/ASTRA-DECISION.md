# A77 decision — master tools for one Minion session

Accepted for queued implementation on 2026-11-21. The first qualification target is a deliberately prepared Claude Code CLI invocation in one Linux tmux session. No harness has passed native qualification yet. The existing Hub nomination action remains admin-only. Destination Workers continue to control which sessions accept tasks. [User request and acceptance](requirements.md) · [Current Minion behavior](discovery.md) · [Harness evidence](capability-matrix.md)

## What the administrator selects

A master is a specific **Worker-visible terminal session**. The Worker must identify one live terminal incarnation and one dedicated harness connection inside it. A chat clear or a child agent using the same harness within that terminal does not by itself end the nomination. A separate terminal, a linked pane shared by two sessions, or a shared harness daemon must never acquire the role through the first connection. A name change, a replacement terminal or harness, or loss of an unambiguous mapping retires the binding. An administrator can nominate the newly identified candidate. Existing installations may have several deliberately nominated masters.

On a prepared invocation, nomination adds a small set of MCP tools with descriptions covering permitted discovery, target inspection, task delivery and delivery outcomes. Revoke removes those tools from the live catalog. Claude's additive launch-scoped `--mcp-config` can register a stdio server for exactly one invocation. Its idle state has zero tools, prompts, resources or master instructions. A neutral server entry can remain visible in that invocation's MCP settings after revocation. Tell users this explicitly. Use inline non-secret configuration if supported. Leave the operator's other MCP servers and plugin settings intact. [Claude CLI options](https://code.claude.com/docs/en/cli-reference) · [Live MCP tool updates](https://code.claude.com/docs/en/mcp#dynamic-tool-updates)

**An already running, unprepared CLI has no verified external live-attachment mechanism.** Show “This session was started without an attachment” and the supported per-session launch option for the user's next deliberate launch. A new invocation has a new identity and requires its own nomination. The Worker must never restart the current session, type setup commands into it, or edit a shared profile. A profile-wide dormant bootstrap would make a server discoverable in unrelated sessions and still miss existing processes. It is outside this decision. No owner action is needed to investigate the per-launch path.

## Authority and revocation

1. **Bind the local connection.** At launch, pin the actual tmux server instance, session and pane IDs, and the harness process lifetime. On Linux use a process handle such as a pidfd. The Worker derives the terminal mapping from the host. A supplied pane, display name, PID, environment variable or private socket path cannot establish it. Use a dedicated local transport. For the CLI fixture, accept a Unix socket connection from the stdio helper, verify the kernel-reported peer and executable and its direct launch relationship to the pinned harness, and pin the live peer before admitting it. Check the mapping again before calls and on host changes. Reject unsupported launch topologies, different PID namespaces without a verified mapping, ambiguous ancestry and missing process information. An inherited private channel is also suitable when a managed host can hand it directly to the intended endpoint. Register one connection per launch. The trust boundary assumes an intact Worker, harness and OS account. Account takeover requires OS isolation. [Linux Unix socket peer credentials](https://man7.org/linux/man-pages/man7/unix.7.html) · [Linux process descriptors](https://man7.org/linux/man-pages/man2/pidfd_open.2.html)
2. **Bind the Hub decision.** The Worker advertises an opaque incarnation only for a live, shared candidate on its authenticated link. In the admin mutation, compare the candidate the person selected, the current Worker owner/enrollment and the live observation. Save a distinct nomination generation. Duplicate requests for the same decision are idempotent. Conditional revocation protects against a stale UI removing a subsequent nomination. Preserve the existing legacy target limit when deliberately converting an old grant. PID, paths, conversation text and credentials need not leave the host.
3. **Keep the capability on the Worker.** Use the existing authenticated Worker–Hub connection. The Hub records a short-lived attachment against that link, enrollment, incarnation and generation. A Worker-internal handle identifies the attachment on scoped calls. It confers no independent bearer authority. Keep it out of MCP parameters, arguments, exported environment, files, audit output and chat. Start qualification with a 30-second lease renewed every 10 seconds on a monotonic local deadline. Push nomination and revocation changes immediately and measure both online and disconnected behavior. These intervals are initial acceptance targets.
4. **Admit each operation at the Hub.** Require a live link and matching attachment, current generation, allowed operation, current two-sided grant and destination scope. Route through the existing authorizer, audit and destination policy, including for targets presented as local. The scoped principal must explicitly intersect the grant with visible Workers and shared sessions. The ordinary Worker principal includes extra access to its own Worker. Return empty discovery when no target consents. Expose scoped listing, bounded snapshot and ordinary guarded agent-prompt delivery with the existing request ID and outcome. Keep raw keys, forced delivery, shell targets, generic pipe and administration outside this catalog. `set_task` edits a label. It cannot substitute for task delivery. [Hub call registrations](../../internal/hub/workers/session_control_calls.go) · [Existing outcome rules](../../internal/llmguide/guide.md)
5. **Serialize revocation with dispatch.** On revoke, invalidate the generation at the Hub before acknowledging the change. Make the final authorization and dispatch admission ordered with concurrent revocation or consent changes. A call admitted after the change must fail, even with cached tools or a stale handle. Cancel still-cancellable work. Previously dispatched writes can finish. Preserve delivered, partial or unknown outcomes and the existing duplicate protections. Never queue offline or automatically resend an uncertain write. Withdraw tools on the supported refresh boundary. Record client reconciliation separately from the Hub's authorization result. Native history can retain earlier instructions and results.

The Worker withdraws the catalog immediately on observed disconnect, lease expiry, share loss, rename, process exit or replacement. End the authenticated attachment on enrollment reset or owner reassignment. On Hub restart or link replacement, old handles are invalid. A surviving Worker may reacquire a lease only after re-proving the same live incarnation and current durable nomination. For the first implementation, Worker restart ends the in-memory incarnation and requires fresh nomination. Revoke deletes any Minion-created master-only runtime material and cleans up its tracked files on recovery. Avoid creating role-specific files at all in the reference mode.

## Upgrade and compatibility

Keep existing name-only grants explicitly labeled **legacy** with their existing behavior. They do not activate an attachment. Store bound nominations separately from records consulted by older `source_session`-only grant lookups. Conversion atomically removes the legacy authorizing row, preserves its restrictions and creates the bound record. Prevent both forms from coexisting, including writes through older administrative APIs. Reject attempts to convert a bound record back to name-only through old clients or retries. Verify downgrade behavior against the previous released Hub on an isolated database. If it opens the newer schema, its normal name-only operations must be unable to reactivate a bound record. Enforce that property in the persisted representation or block incompatible downgrade in the supported upgrade path before enabling binding. Mixed-version peers report the missing capability. Existing unrelated owner/admin API credentials keep their independent authority. The scoped adapter must never fall back to them, the generic local executor, or ordinary REST. Prepare one invocation. Capture its empty → active → empty catalog and the other session's unchanged catalog. Check native refresh failure, retained idle connection, clearing the chat, same-name recreation, helper reconnect, linked/moved panes and a sibling presenting copied pane or connection fields. Verify the kernel peer and observed parent topology on the exact launch path. Report which user-visible refresh boundary was observed. Simulate lease expiry, disconnection, reconnect, reset and restart with a controllable clock.
3. **Ship the qualified attachment and status.** Show the selected session's nomination, supported launch mode, actual attachment and cleanup state independently. Provide session-only setup guidance. List the exact qualified versions and platforms. Codex, Gemini, OpenCode, macOS and Windows need their own isolation and refresh evidence before being advertised. Keep this release after recovery and Usage. An installable candidate must pass these checks on its exact revision.
