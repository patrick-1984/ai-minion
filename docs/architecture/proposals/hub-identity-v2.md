## 1. Goal and non-goals

Today (0.6.2) a Hub has one Ed25519 identity key, `identity.key`, stored in plain form. Workers pin its fingerprint, `mnk_` invitation keys name it, it signs every handshake and every revoke, and a copy of it sits in every backup. Whoever holds that file is the Hub for every Worker, for ever, and a stolen backup is a permanent Hub impersonation that only a new identity and re-enrollment of all Workers repairs.

Goal (owner roadmap F-05, owner decision of 2026-11-12): the Worker verifies the Hub through a short-lived certificate; the long-lived **root key** stays on the Hub but is **sealed**: encrypted at rest with a passphrase that the owner chooses, types by hand and keeps somewhere else, and that the Hub never stores. A stolen disk or backup then does not hand over the root key as long as the passphrase is strong. Onboarding stays as simple as it is now: the same `mnk_<fingerprint>.<secret>` invitation, the same `MN-XXXX-XXXX` code, no extra step for a normal user. The Hub restarts and serves unattended, because the operational key and the current certificate are not sealed.

The price, stated plainly: nothing can issue a certificate without the owner. There is no automatic renewal. The owner re-issues the certificate (default validity 180 days) from a dedicated page of the web UI or from the command line, and types the passphrase each time.

Non-goals (design decision): no Worker certificates (a Worker proves its key as today; the owner roadmap sketch for F-05 also mentions them, and this design does not deliver them); no certificate revocation list; no change of the invitation key format; no automatic renewal; no recovery of a forgotten passphrase; no hardware-backed or remote signers; no certificate history table (the history is the audit log); no change of the CPace construction.

## 2. Threat model: what this protects and what it does not

The protection is exactly this: **the root key is not readable from a copy of the disk, a data-directory copy or a backup unless the attacker also learns the passphrase, and the passphrase can only be guessed offline at the speed of the key-derivation function.** It does not protect against an attacker who is inside a running Hub at the moment the owner types the passphrase.

| Event | Result in 0.7 (this design) | Result in 0.6.2 |
| --- | --- | --- |
| A disk, a data-directory copy or a backup is stolen (the Hub is not under attacker control) | The thief holds the sealed root, the operational key (plain, so the Hub can restart unattended), the current certificate and the database. The **operational key** lets the thief impersonate the Hub to a Worker that has not yet seen a later serial, until the `not_after` of the certificate that names it (180 days by default, at most 400); the owner ends this early by re-issuing the certificate (section 8), which creates a **new** operational key. The **root key** stays safe if the passphrase is strong (section 10.3): the thief has unlimited offline guesses but each costs one scrypt run. If the passphrase is weak, this is a root compromise (next row). | Permanent. |
| The passphrase is guessed, phished, shoulder-surfed or read while it is typed, together with a copy of the sealed root | **Root compromise.** The certificate lifetime does not bound it. A key rotation does not repair it either: a thief with the old root can sign a competing transition. Workers must be re-pinned out of band (new identity, every Worker reset and enrolled again, as 0.6.2 already documents). | Same. |
| A live Hub compromise: the attacker runs code as the Hub's user or reads the Hub's memory | Without the passphrase being typed: the attacker has the operational key and the database, not the root; the damage is bounded by the certificate as in the first row, and no new certificate can be signed. **While the owner types the passphrase on that Hub (web UI or command line), the attacker can capture it from memory or from the request, and then holds the root.** This design does not protect against that. The attacker also reads whatever the Hub stores of the sessions; that is the existing trust in the Hub. | Root is a plain file: compromise. |
| The reverse proxy in front of the web UI is hostile or compromised | It sees the passphrase of every UI operation in clear text (TLS ends there). Operators who do not trust it use the command line, which talks to the Hub over the local socket (section 8.3). | Not applicable. |
| An administrator session is stolen | The thief cannot issue anything: every identity operation needs a fresh re-authentication **and** the passphrase (section 8.1). | Same session power as today. |
| The passphrase is forgotten | No recovery by design (section 10.7). The Hub keeps serving until its certificate expires; then the only way back is a new identity and re-enrollment of all Workers. | Not applicable. |
| The owner does not re-issue in time | The Hub stops accepting Workers at `not_after` (Workers also stop trusting it, section 11.3). The web UI keeps working; pairings are not touched. Re-issuing fixes it (section 8.4). | Not applicable. |
| A man in the middle presents its own key | Refused: the root is pinned (or named by the invitation) and the certificate must verify under it. | Same. |
| A Worker clock is wrong | The cut-off moves by the same amount; a Worker whose clock is more than one hour before `not_before` refuses the Hub (`cert_not_yet_valid`). Documented in `docs/security.md`. | Not applicable. |
| A removed Worker is offline when the certificate expires | It receives its revoke at the first successful handshake after the next certificate; until then it stays paired and refuses the Hub. | Not applicable. |

What the design does **not** do: it does not make the Hub trustworthy for session content (see "Who sees what" in `docs/security.md`), it does not protect against a root compromise, it does not protect against a live attacker on the Hub while the passphrase is typed, it does not protect a Worker that is offline for the whole remaining life of a stolen certificate, and it does not review the CPace construction (the independent review stated in `docs/security.md` is still pending).

## 3. Key hierarchy and files

- **Root key** (Ed25519, the key format of today's `identity.key`: header `minion-ed25519-seed-v1:` plus the seed). It is the Hub's long-lived identity, also called the **master key** in the UI. Its fingerprint is what Workers pin and what `mnk_` keys and pairing name. It signs only hub certificates (purpose `hub-cert`) and root transition records (purpose `transition`). On disk it exists only **sealed** (section 10.1); in memory it exists only during one operation.
- **Operational key** (`op.key`, same format, plain, mode 0600). It signs the handshake (`hs-hub`), the CPace confirmation (`pake-confirm`) and revocations (`revoke`). It lives on the Hub in plain form and is loaded at start.
- The two keys differ; a certificate with `root_pub == op_pub` is invalid.
- Fingerprints, encodings and the signing rule are those of 0.6: a fingerprint is the lowercase base32 (no padding) of the SHA-256 of the 32-byte public key, 52 characters; binary JSON fields are base64url without padding; every signature is Ed25519 over `"minion/v1/<purpose>" || 0x00 || data`, applied once by `identity.Sign`. The purposes are `hs-hub`, `hs-worker`, `transition`, `revoke`, `pake-confirm` and the new `hub-cert`; the list stays closed (`internal/identity/sign.go`).
- "The Hub fingerprint" always means the root fingerprint.

Data directory files (design decision for the names; modes 0600):

| File | Meaning |
| --- | --- |
| `root.key.age` | the sealed root: the root key file encrypted with the owner passphrase (age, scrypt recipient) |
| `root.key.age.next` | a sealed root that is staged and not yet renamed over `root.key.age`: the new root of a master-key rotation, or the same root under a new passphrase |
| `op.key` | the operational key in use |
| `op.key.next` | an operational key that is staged or whose certificate is committed, not yet renamed over `op.key` |
| `identity.key` | exists only on a Hub migrated from 0.6 that has no passphrase yet (section 9.7); removed when the passphrase is set |
| `data.key`, TLS files | unchanged |

The current certificate is stored in the database only (no certificate file), so it can never disagree with the serial state. The database also records the SHA-256 of the current sealed root file (section 7), so recovery can tell which sealed file is current without the passphrase.

## 4. One rule: every certificate has a new operational key (design decision)

There is **no same-key renewal**. Every issuance, the first one and every re-issue, generates a new operational key and certifies that key. "Re-issue the certificate" and "rotate the operational key" are one operation, named `reissue` (there is no second name).

Consequence: a stolen operational key is bounded by the validity of **its own** certificate. Issuing a later certificate never extends it, because the later certificate names a different key that the thief does not have. The thief cannot use the new certificate (certificates are public, but a handshake needs `sig_hub` by `cert.op_pub`), and a Worker that has seen the new serial refuses the old one.

The price is that every issuance closes all Worker sessions (section 9.6; they must be recycled anyway, because a Worker fixes its deadline at the handshake). If the owner re-issues when the 30-day warning starts, that is one reconnect per Worker about every 150 days.

## 5. Certificate

All integers are big-endian two's complement. No optional field, no padding, no trailing data.

| Offset | Size | Field | Rule |
| --- | --- | --- | --- |
| 0 | 1 | `version` | exactly `0x01` |
| 1 | 32 | `root_pub` | Ed25519 public key of the root |
| 33 | 32 | `op_pub` | Ed25519 public key of the operational key; differs from `root_pub` |
| 65 | 8 | `serial` | unsigned, `1 .. 2^63-1` (top bit clear) |
| 73 | 8 | `not_before` | signed, Unix milliseconds UTC, `>= 0` |
| 81 | 8 | `not_after` | signed, Unix milliseconds UTC |
| 89 | 64 | `signature` | Ed25519 by the root over the payload (offsets 0 to 88) |

- **Payload** = offsets 0 to 88, 89 bytes. **Wire certificate** = payload followed by the signature, **153 bytes**; JSON form base64url without padding, 204 characters.
- **Signature** = `identity.Sign(root, "hub-cert", payload)`, which signs `"minion/v1/hub-cert" || 0x00 || payload`. The prefix is applied once, by `Sign`; the payload does not contain it.
- **Validity.** `d = not_after - not_before` is computed with overflow checking; valid only when `0 < d <= 34,560,000,000` ms (400 days). All arithmetic on these fields (the difference, the `not_before - 1 h` tolerance, the serial increment) is checked: an overflow is a rejection, never a wrap.
- **Identity of a certificate** for the Worker's equal-serial rule is the SHA-256 of the 153 bytes.
- Default validity **180 days** (design decision; `not_before` = the instant the serial is allocated). `--validity D` (whole days, 1 to 400) and the UI field apply to **that issuance only**; there is no persistent validity setting and nothing renews a certificate by itself (section 8.4).

**Parse and verify order** (`identity.ParseHubCert`, then `Verify(rootPub)`): (1) length 153; (2) `version == 1`; (3) `root_pub != op_pub`; (4) `serial` in `1..2^63-1`; (5) `not_before >= 0` and `0 < not_after - not_before <= 400 d`, checked; (6) `cert.root_pub` equals the root the caller expects and the signature verifies under it. The first failing step names the reason: `cert_malformed` for 1 to 5, `cert_root_mismatch` or `cert_bad_signature` for 6.

## 6. Serials

- **Allocation.** `serial = max(last_issued + 1, now_ms, floor + 1)`, where `now_ms` is the Hub wall clock in Unix milliseconds and `floor` is the operator's `--serial-floor N` (0 when absent; "the new serial must be greater than N"). The increment is checked; an allocation beyond 2^63-1 fails. Allocation sets `last_issued = serial` in the same transaction that stores the certificate. A floor above `now_ms + 366 days` is refused with `invalid_argument` unless `--allow-far-floor` is given, so a typing error cannot burn the serial space.
- **The guarantee, scoped (design decision).** *Within one issuance lineage, no serial is allocated twice and no serial is ever issued with two different payloads.* An issuance lineage is one database in which every allocation was committed before use and that was never replaced by an older copy, lost, or forked into two Hubs that both issue. A wall-clock rollback alone cannot repeat a serial, because `last_issued` is durable and the allocation takes the maximum. Uniqueness is lost only when the issuance state itself is **restored from an older copy, lost, or forked** (for example two Hubs started from one backup): the database may then not know serials that Workers have seen, and a new allocation can equal one of them. The design does not try to prevent that; it **detects** it at the Worker and gives the operator a recovery command.
- **Worker memory.** A Worker stores, in its enrollment row and scoped to the pinned root, `max_serial` and `cert_sha256` (SHA-256 of the 153 bytes seen at `max_serial`). It raises `max_serial` and never lowers it. It refuses a certificate with `serial < max_serial` (`cert_serial_too_low`) and one with `serial == max_serial` but a different hash (`cert_serial_conflict`). They reset only when a verified root transition changes the pin (a new root starts a new scope at 0). A pin from 0.6 has `max_serial = 0` and no hash.
- **Recovery (N1; operator-controlled, no report on the wire).** A refusing Worker ends the handshake after `sig_hub` verified, without sending `sig_worker` and without any frame that names its value, and writes one local log line with the certificate serial, its own `max_serial` and the exact command: `minion hub identity reissue --serial-floor N` with `N = max_serial`. The Hub never learns the value from the wire, so a hostile Worker cannot move the serial counter. The operator takes the highest `max_serial` among the refusing Workers and runs the command (it asks for the passphrase); Workers reconnect and accept the new certificate.
- **Restore.** A restore installs the backed-up certificate and does not issue (section 13). If Workers refuse it because they saw a later serial, the operator uses the recovery command.
- Two separate cases, two separate test groups (section 17): an **ordinary restore** (older state, correct clock) and a **collision** (restored or forked issuance state allocates a serial a Worker already holds with different bytes).

## 7. Durable Hub state (forward-only migration)

One forward-only `sqlmigrate` migration (design decision) extends the existing singleton `hub_identity` row (no history table; the history is the audit log). All serials fit SQLite's signed integer.

| Column | Meaning |
| --- | --- |
| `last_issued` INTEGER NOT NULL DEFAULT 0 | the highest serial ever allocated |
| `current_serial` INTEGER NOT NULL DEFAULT 0, `current_cert` BLOB (NULL or 153 bytes) | the certificate in use ("C") |
| `root_sealed` INTEGER NOT NULL DEFAULT 0 | 0 while the root is still the plain `identity.key` of 0.6 (or no root exists yet), 1 once the sealed root is recorded |
| `root_file_sha256` BLOB (NULL or 32 bytes) | SHA-256 of the current `root.key.age`; lets recovery choose between `root.key.age` and `root.key.age.next` without the passphrase |
| `migrated_from_06` INTEGER NOT NULL DEFAULT 0 | set by the migration of a 0.6 identity; cleared by the first master-key rotation (drives the banner of section 14) |

Every change of these columns is one `BEGIN IMMEDIATE` transaction followed by `MakeDurable`; the ordering and failure rules are those of section 9.1, defined once. ## 8. Operations: the identity page and the commands (design decision)

Four operations touch the root, and each needs the passphrase: **set the passphrase** (first start and migration), **re-issue the certificate**, **rotate the master key**, **change the passphrase**. They are executed by the running Hub (catalog actions `hub_identity_set_passphrase`, `hub_identity_reissue`, `hub_identity_rotate` (the existing admin operation, now sealed) and `hub_identity_change_passphrase`). The Hub holds its **rotation mutex** for the whole of every identity change, so no file locking against a running Hub is needed. The commands that run without the passphrase are the read-only `minion hub identity`, `minion hub backup` and `minion hub restore` (restore with the Hub stopped). Removing a Worker and its revoke need no passphrase: they are signed by the operational key.

### 8.1 Authorization (all four operations, UI and REST)

1. **Administrator role.** Other roles get `forbidden`; the page and its buttons are not shown to them.
2. **Fresh re-authentication (contract; design decision).** Released sessions carry no authentication time or login method, so this design adds them, owned by the server only:
   - The session record gains `auth_at` (Unix ms) and `auth_method` (`local` or `oidc:<provider id>`). They are written only by the server, only after a credential check that the server itself performed (local password verified, or an OIDC callback whose ID token passed verification, see below). No request field, header or cookie can set them. A session created without such a check (for example by a silent SSO redirect that returned no verifiable `auth_time`) has `auth_at = 0` and is never fresh.
   - The operation is allowed only if `now - auth_at <= 5 minutes` for the session of the request. The server checks this on every operation and answers `reauth_required` otherwise. Neither the operation nor any other request extends `auth_at`; only a re-authentication does.
   - **Re-authentication** is `POST` to a new endpoint bound to the current session (the session id and CSRF token are part of the request and of the stored state): `local`: the account password is verified again; `oidc`: the Hub starts a new authorization request with `max_age=0` and `prompt=login` (the request builder of `internal/hub/auth/oidc/provider.go`, near line 318, today requests neither), stores a one-time state and nonce bound to this session, and in the callback verifies the ID token as for a login **and additionally** requires an `auth_time` claim that is not earlier than the moment the request was started (30 seconds of clock allowance) and the same subject as the session. Only then are `auth_at` and `auth_method` updated, on that same session.
   - **Fail closed.** If the provider does not return `auth_time`, ignores `max_age`, returns a different subject, the state is unknown, expired or used, or freshness cannot be established in any other way, the answer is `reauth_unavailable` and nothing is updated. A new session, a plain SSO redirect without verified `auth_time`, or a refreshed token is not a fresh credential check.
   - A failed re-authentication is audited as `hub_identity.reauth_failed` (section 8.5) and never counts as a passphrase failure.
3. **The passphrase** in the same request (never in the URL, never in a header).
4. **CSRF.** Every operation is a POST with a JSON body (other content types are refused); it needs the synchronizer token of the session, a same-origin `Origin` header (and `Sec-Fetch-Site` when sent), and the session cookie is `SameSite=Strict`. A missing or wrong token is `forbidden` and does not count as a passphrase failure.
5. **Transport.** The passphrase is accepted only on a request whose **effective browser scheme is HTTPS**, decided by the Hub's existing trusted-proxy rules (the effective-scheme logic of `internal/hub/server/publicurl.go`, near line 143): the TLS state of the connection itself, or a forwarded protocol header that counts only when the immediate peer is inside the configured trusted-proxy networks. The loopback address of the peer is **never** by itself a reason to accept cleartext, because a local reverse proxy forwards remote browsers from loopback. Forged forwarded headers from an untrusted peer are ignored. The only HTTP exception is an explicitly configured local management interface (a listener bound to a loopback address and marked as the management listener in the Hub configuration, not the listener to which a proxy forwards); everything else is refused with `tls_required`. Responses carry `Cache-Control: no-store`; the page sets `autocomplete="new-password"` or `"current-password"` on the passphrase fields and clears them after every submission.
6. **Rate limit.** At most 10 web identity operations per hour for the Hub as a whole (the **web allowance**), and the persistent passphrase lockout of section 10.6. Local CLI unseal operations have their **own hourly allowance** (10 per hour, counted separately), independent of the web allowance, so an exhausted web allowance never blocks the owner at the Hub host. A request refused because of a lock (web or local) does **not** consume allowance; an attempt that reaches the key derivation consumes one unit of its own scope's allowance, whether the passphrase is right or wrong. The checks run in the order above and then item 8; the key-derivation function runs only after all of them passed.
7. **One operation at a time** (the rotation mutex). A second request waits at most 5 seconds, then answers `conflict`.
8. **State check (server authorization of set-passphrase).** `set-passphrase` is accepted by the server only in bootstrap state B0 or B1 (section 9.7: `root_sealed = 0`). In any other state, including B2 (a sealed root is recorded and only the certificate is missing), the answer is `conflict` ("a sealed root exists; use re-issue certificate") and nothing is read, unsealed, written or counted. Set-passphrase never replaces, overwrites or re-seals a recorded sealed root. The UI shows the action under the same condition, but the server does not rely on the UI.

### 8.2 The page (admin only; "Settings", "Hub identity")

The page shows, from the database and without any passphrase: root fingerprint, operational key fingerprint, current serial, `not_before`, `not_after` with the days left, the state of the passphrase ("set" or "not set yet"), the date of the last successful operation and the lockout state. Banners: "Set the Hub passphrase" while none is set (Workers cannot connect); the expiry banner of section 8.4; "Rotate the master key" on a Hub migrated from 0.6 (section 14).

| Action (button) | Fields | Effect |
| --- | --- | --- |
| **Set passphrase** (visible only in B0/B1, that is while `root_sealed = 0`) | new passphrase, confirmation | Section 9.7: seals the root (creating it on a new Hub), then issues the first certificate. **Only while `root_sealed = 0`** (UI and server, 8.1 item 8); in B2 (sealed root, certificate missing) the action is not shown and is rejected, and the owner uses **Re-issue certificate** with the existing passphrase. |

### 8.3 Commands (same four operations, terminal)

| Command | Behaviour |
| --- | --- |
| `minion hub identity` | Read-only, works with the Hub stopped. Prints what the page shows. Needs no key file and no passphrase. |
| `minion hub identity set-passphrase` | As the page action. |
| `minion hub identity reissue [--validity D] [--serial-floor N] [--allow-far-floor]` | As the page action. |
| `minion hub identity rotate` | As the page action: asks for the current passphrase, then the new one twice, then the word `ROTATE`. |
| `minion hub identity change-passphrase` | As the page action. |

The command **prompts for the passphrase on the terminal** with echo off and **refuses to run when standard input is not a terminal**; there is no flag, environment variable or file for the passphrase (design decision). It sends the passphrase to the running Hub over the local Unix socket (mode 0600, the Hub's own user), which is where the Hub process holds the mutex and does the work; the passphrase never crosses the network or the reverse proxy. Authorization is the operating-system permission on the socket plus the passphrase itself; the fresh re-authentication of 8.1 applies to the web UI only. The commands have their **own** failure counter, lockout and hourly allowance (section 10.6 and 8.1 item 6), separate from the web ones, so that a lockout caused through the web does not lock the owner out at the Hub host. The command's actor is the operating-system user taken from the kernel credentials of the socket peer (never from client input). The Hub's REST authorization and CSRF do not apply to the socket, which is not reachable from a browser.

### 8.4 Expiry policy (design decision)

- **Validity.** Default 180 days per issuance, at most 400 (the certificate format). Nothing renews a certificate automatically, because a renewal needs the passphrase and the Hub never holds it.
- **Warnings from 30 days before `not_after`.** (1) A banner on every page for administrators: "The Hub certificate expires on DATE (N days). Re-issue it." (2) The Workers page shows the countdown in its header. (3) The Hub logs one warning line at every start and then every 24 hours; from 7 days before expiry the line is at error level and the banner is red. (4) The audit event `hub_identity.expiry_warning` is written once per UTC day while the warning is active. (5) A Worker that connects to a certificate with fewer than 30 days left logs one warning line.
- **At expiry** (`now >= not_after`). The Hub closes every Worker session, refuses new Worker connections with HTTP 503 and code `hub_cert_expired` (a new code in `proto/codes.go`) before the upgrade, and writes the audit event `hub_identity.expired` once. The web UI, REST API and commands keep working so that the owner can fix it. Pairings, pins and Worker data are untouched. The fix is "Re-issue certificate"; Workers reconnect by their normal backoff.
- **The Worker enforces expiry itself** (section 11.3), independently of the Hub, with the monotonic and the wall clock; a Hub that keeps a connection open past `not_after` is cut by the Worker.
- **A restart does not need the passphrase**, also after expiry: the Hub starts, serves the UI, and refuses Workers until the certificate is re-issued.

### 8.5 Audit events

All events carry the actor, the channel (`ui`, `cli` or `system`), the result, and, where they exist, the serial and the fingerprints. **No event, log line or error contains a passphrase, a part of it, or its length.**

- **Actors (authoritative).** `ui`: the authenticated user id of the session. `cli`: `local:<uid>` with the user name, taken from the kernel peer credentials of the Unix socket (section 8.3). Automatic events (`expiry_warning`, `expired`) have the **system actor** `system:identity-expiry` and channel `system`; the warning is written once per UTC day by the Hub's timer, in its own transaction, with a unique key per day so that a restart does not repeat it.
- **Same transaction.** Every identity state change writes its audit row **in the same transaction** as the change, as released `internal/hub/workers/rotate.go` does (near line 254): `passphrase_set`, `passphrase_change`, `reissue` and `rotate` are inserted by the transaction of step 5 of 9.2 (and of the bootstrap and passphrase-change transactions), so a committed change always has its row and a rolled-back one has none. Generic API-layer auditing is not used for these operations, because it can fail after the change succeeded.
- **Lockout events.** `unseal_failed` and `locked` are inserted in the same transaction that updates `unseal_failures` and `unseal_locked_until` (or their command counterparts), with the counter value and the lock end time in the row; `reauth_failed` is inserted by its own small transaction.

`hub_identity.passphrase_set`, `hub_identity.passphrase_change`, `hub_identity.reissue`, `hub_identity.rotate`, `hub_identity.reauth_failed`, `hub_identity.unseal_failed` (with the failure count, never the reason class), `hub_identity.locked`, `hub_identity.expiry_warning`, `hub_identity.expired`.

## 9. Activation, durability and recovery (one implementation)

The first certificate, every re-issue and every master-key rotation use **the same procedure, the same crash tables and the same recovery code**. They differ only in how the new key set is staged. A passphrase change uses the durability rules and a small table of its own (9.4). Notation: K = `op.key`, N = `op.key.next`, RK = `root.key.age`, RN = `root.key.age.next`, C = the current certificate.

### 9.1 Durability rules (the only definition)

- **D1 Whole files.** A private key file (plain or sealed) is written to a temporary name, synced, and renamed to its final name; it never exists under its name incomplete.
- **D2 Directory sync before commit.** Every key file that a transaction is about to name is on disk **and its directory entry synced** before that transaction commits: N staged (and RN in a rotation or a passphrase change), then the directory synced. The directory is synced again after every later rename (N to K, RN to RK).
- **D3 Committed but unconfirmed** (the branch of `rotate.go` near lines 270 and 446). Every transaction ends with `MakeDurable`. If it returns `ErrCommitNotDurable` (a checkpoint failure, or a request canceled between COMMIT and the checkpoint), the commit may or may not survive a power loss. The operation retries the confirmation once, detached from the request context. Until a confirmation succeeds nothing may use the new state: no handshake, no in-memory swap, no rename over K or RK; N and RN stay where they are, the Hub keeps its previous pair, records the unconfirmed activation in memory, and refuses every other identity change with `conflict` ("repeat the same command to confirm"). The same command (or the next start) confirms and completes it. The passphrase is not kept for this: the owner types it again, and a repeated command that finds its own effect already committed completes without a new unseal where it can (renaming and swapping need no root).
- **D4 Preservation.** A key file whose public key equals `C.op_pub` is never deleted, overwritten or moved aside, under the names K or N; a sealed file whose SHA-256 equals the recorded `root_file_sha256` is never deleted or overwritten except by the rename of the file that replaces it after its commit is confirmed. A staged file that matches neither the recorded state nor a committed one has never signed or served anything and is removed by recovery (9.5).
- **D5 Failed rename after a durable commit.** The Hub keeps serving from its in-memory (key, certificate) pair, logs an error naming the files, and refuses every further identity change with `conflict` until a retry of the rename succeeds. It never writes another N or RN.
- **D6 Directory-sync failure.** Before the commit (D2): the transaction is not started, the staged files are removed, and the operation fails with nothing changed. After a rename (step 7): the rename took effect in the running file system, so the Hub treats this like D5: it keeps serving the in-memory pair, logs an error, records "directory sync pending" in memory, refuses further identity changes with `conflict`, and retries the (idempotent) rename and directory sync on the next identity request and at every start. If power is lost before a sync succeeded, the rename may be undone and the files are in the state of A3 or X3, which recovery completes.
- **D7 Sessions are closed after every swap.** From the moment the in-memory swap (step 6) happened, closing all registered Worker sessions (step 8) is guaranteed on every path: it is registered as a deferred action immediately after the swap and runs also when the rename, the directory sync or a later step returns an error or panics. An error after the swap never skips the closure.

### 9.2 The activation procedure

Under the rotation mutex, with the passphrase(s) of the operation in memory:

1. **Recover** any pending state with the rules of 9.5; if something is unresolved, refuse with `conflict` naming the files.
2. **Unseal** the root: read RK, check that its SHA-256 equals `root_file_sha256`, decrypt with the passphrase (section 10), check that the public key equals the recorded root. A failure here changes nothing and counts for the lockout (10.6). In a master-key rotation also generate the new root in memory, seal it under the new passphrase to RN (D1), decrypt it back once with the new passphrase to prove the file and the passphrase agree, and sync the directory (D2).
3. **Stage** a fresh operational key at N (D1, D2); refused with `conflict` if N exists after step 1. The seeds of the new keys are held only in destroyable signers (section 10.4).
4. **Sign.** Allocate the serial; sign the certificate with the root through the operation-scoped destroyable signer (section 10.4; in a rotation: the transition record with the old root's signer, the certificate with the new root's signer). Every signer is destroyed, and the decrypted key-file plaintext and the seeds are wiped, immediately after the last signature and on every exit path, before the transaction.
5. **Transaction:** store the certificate as `current_cert`/`current_serial`; for a rotation also the transition record, the new identity row, the new `root_file_sha256`, `migrated_from_06 = 0` and the revoked invitations; **insert the audit row of the operation (section 8.5) and reset the lockout counters of the scope in use**; commit; `MakeDurable` (D3). A certificate is served only after this step returned success.
6. **Swap** the (operational key, certificate, root) set in memory as one value and increment the activation generation (9.6).
7. **Rename** RN over RK (rotation), N over K; sync the directory (D2, D5).
8. **Close** all registered Worker sessions (9.6); guaranteed after every swap by D7.

### 9.3 Crash points: direct activation (first certificate and re-issue)

Recovery runs before any listener opens, and again at the start of every identity change under the mutex. "Power loss" means the database may be older than the files (a commit that was not yet durable can vanish); D2 and D3 exclude the opposite case (files older than a durable database).

| # | Crash point | Durable facts | Recovery | Operator-visible result |
| --- | --- | --- | --- | --- |
| A1 | N staged and synced, transaction not committed, or the commit is lost to power loss | N matches neither C nor anything recorded | N never served anything: remove it | repeat the command |
| A2 | transaction committed (visible), `MakeDurable` not returned or failed | N matches `C.op_pub` (visible) or nothing (lost) | D3: confirm durability first; if it fails the Hub keeps its previous pair and N, and refuses to start if the confirmation keeps failing at start; if the commit was lost, A1 applies | repeat the command: it confirms and completes |
| A3 | commit confirmed (the in-memory swap may or may not have happened), before the rename of N over K, or a rename whose directory sync was lost to power loss | N matches `C.op_pub` | **file recovery:** rename N over K, sync the directory, then serve | none, or repeat the command |
| A4 | after the rename of N over K and its directory sync | files complete | none (a rename not yet synced when power failed is A3) | none |
| A5 | after the swap (and possibly after the rename), before all sessions are closed | the process is gone, so no session exists | **session-only: no file action.** A3 and A4 decide about files; A5 only states that no stale session can exist after a restart (D7 covers the live-process case) | none |

### 9.4 Crash points: master-key rotation (two files) and passphrase change

**Master-key rotation (compound: RN, N and the database):**

| # | Crash point | Durable facts | Recovery |
| --- | --- | --- | --- |
| X1 | RN and N staged (synced), transaction not committed or lost | database records the old root and the old `root_file_sha256`; RN and N match nothing | RN is removed (it never signed anything; the old sealed root is still RK); N is removed (A1) |
| X2 | committed, not confirmed | database may be old or new | as A2 for both files; the Hub keeps its previous identity until D3 confirms |
| X3 | committed and confirmed, neither file renamed | RN's SHA-256 equals the recorded `root_file_sha256`, N matches `C.op_pub` | rename RN over RK and N over K, each decided independently |
| X4 | RK renamed, N not (or the reverse) | one pending file left | complete the pending one; the decision for each file looks only at its own match |
| X5 | both renamed | complete | none |

**Passphrase change** (RN is the same root sealed under the new passphrase; nothing else changes, no generation, no session closes):

| # | Crash point | Durable facts | Recovery |
| --- | --- | --- | --- |
| W1 | RN staged and verified (decrypted back), transaction not committed or lost | recorded `root_file_sha256` is that of RK; RN does not match | remove RN; the old passphrase still opens RK; repeat the command |
| W2 | committed, not confirmed | database may be old or new | D3: the result is not reported until confirmed; the old or the new passphrase applies according to which state survives, and the owner learns which by the repeated command |
| W3 | committed and confirmed, RN not renamed | RN matches the recorded hash | rename RN over RK |
| W4 | renamed | complete | none |

### 9.5 Recovery rules

- **A. Pending N at start** (D4 applies). Public key equals `C.op_pub`: confirm durability (D3), then rename over K. Matches nothing: remove it. Afterwards K must equal `C.op_pub`, or the Hub refuses to start and names the files. A missing K with an N that cannot complete it is the same refusal; the Hub generates nothing.
- **B. Sealed root files.** Of RK and RN, the one whose SHA-256 equals the recorded `root_file_sha256` is the root. An RN that matches is renamed over RK after the confirmation of D3; an RN that does not match is removed. If neither file matches, or both are absent while `root_sealed = 1`, the Hub refuses to start, names the files, and generates nothing (fail closed; restore the file from a backup). Recovery never reads a sealed file's content: it needs no passphrase.
- **C. Plain residue.** While `root_sealed = 1`, an `identity.key` or `identity.key.next` left in the data directory is plain root material from 0.6. **It may be deleted only after a successful `MakeDurable` confirmation of the commit that recorded `root_sealed = 1` and the matching `root_file_sha256`, regardless of which sealed file name (`root.key.age` or `.next`) is involved.** Recovery therefore runs the confirmation (D3) first; if it fails or cannot run, **both the plain file and the sealed file are kept**, the Hub refuses to start Worker service and names the files. Only after the confirmation is the residue overwritten with zeros where the file system allows, unlinked, directory synced, and logged. While `root_sealed = 0` it is the root and is never touched (9.7).

### 9.6 Activation fence (design decision)

A certificate becomes current in the one procedure above. The **activation generation** is a 64-bit counter in the Hub process starting at 1 that rises at step 6 of every activation: first certificate, re-issue and master-key rotation. **A rotation is not an exception: it swaps the full snapshot (root, operational key, certificate), increments the generation, and closes all sessions.** A passphrase change does not touch the snapshot and does not increment it. A Worker handshake takes the (key, certificate) pair and the generation **once, together**, at admission. Registration in the Hub's registry compares that generation with the current one under the registry lock; if it differs, the connection is closed and the Worker retries with backoff. Since step 6 precedes step 8, a handshake that stalled across the swap either registered before step 6 (and step 8 closes it) or fails at registration; no session survives with the old signer. After a rotation the Workers reconnect and follow the chain (section 11.2).

### 9.7 Bootstrap: setting the passphrase and the first certificate (design decision)

The first certificate has no previous certificate C and no previous operational key K, and the root may not be sealed yet. The state that a Hub is in follows the rule of released `internal/hub/workers/identity.go` (near line 120): a key file that is missing while the database records the identity is **never regenerated**.

| State | Durable facts | What start does |
| --- | --- | --- |
| **B0 pristine** | no `hub_identity` row; none of `identity.key`, `identity.key.next`, `root.key.age`, `root.key.age.next`, `op.key`, `op.key.next` | opens the web UI and commands only; no Worker listener. The page asks for the passphrase (**set passphrase**) |
| **B1 plain identity** | row exists (a migrated 0.6 identity), `root_sealed = 0`, `identity.key` present and its public key equals the recorded root | same: waits for **set passphrase**; the root is `identity.key`, unchanged |
| **B2 sealed, no certificate** | `root_sealed = 1`, `current_cert` NULL, RK matches `root_file_sha256` | waits for **re-issue certificate** (it issues the first certificate); no Worker listener |
| **B3 established** | `root_sealed = 1`, `current_cert` set | normal recovery of 9.5; **fail closed**: a missing sealed root or a missing `op.key` that no `op.key.next` can complete refuses to start, names the files and generates nothing |

A row whose root file (plain or sealed) is missing is **not** B0: it is the fail-closed case (restore the file from a backup). The registry accepts no Worker connection while `current_cert` is NULL.

**Set passphrase**, allowed only from B0 or B1 (never from B2 or B3, and never replacing a recorded sealed root; 8.1 item 8), from B0 (new Hub): validate the passphrase (10.3); generate the root in memory; seal it to RK with D1 and decrypt it back to prove the file; one transaction inserts the row (`pub`, `fingerprint`, `created_at`, `root_sealed = 1`, `root_file_sha256`) and the audit row `passphrase_set`; then the first certificate is issued at once with the root still in memory (steps 3 to 8 of 9.2; the passphrase is not asked twice); then the root is wiped. **From B1:** read `identity.key`, check its public key against the recorded root, seal that same key to RK, decrypt it back; one transaction sets `root_sealed = 1` and `root_file_sha256` and inserts the audit row; only after `MakeDurable` has **confirmed that very commit** (D3; no deletion on an unconfirmed commit, rule C of 9.5), the plain file is overwritten with zeros where the file system allows, unlinked, and the directory synced; then the first certificate is issued as above. The fingerprint, the pins and the `mnk_` invitations of a migrated Hub are unchanged.

**Crash points of the first issuance:**

| # | Crash point | Durable facts | Recovery |
| --- | --- | --- | --- |
| BS1 | B0: RK written, row not written | RK matches nothing recorded; no root exists | remove RK (nothing depends on it); the owner repeats **set passphrase** |
| BS2 | B1: RK written, transaction not committed or lost | `root_sealed = 0`, `identity.key` still the root, RK matches nothing | remove RK; repeat |
| BS3 | transaction committed, not confirmed | database may show B1 or B2 | D3: no listener opens; confirm, then proceed as BS4; if confirmation fails or keeps failing the Hub refuses to start and **keeps both the plain `identity.key` and the sealed file** (rule C of 9.5 applies to RK exactly as to RN) |
| BS4 | committed **and confirmed**, plain `identity.key` still present | B2 plus plain residue | rule C removes it (only after the confirmation just described), then B2 |
| BS5 | B2: first certificate issuance | as A1 to A5 of 9.3 | as in 9.3; the owner repeats **re-issue certificate** after A1 |

After a power loss that loses the commit but keeps the files, the state is BS1 or BS2. The Hub never serves a Worker before B3 is complete and confirmed.

## 10. The sealed root and the passphrase (design decision)

### 10.1 The sealed file

`root.key.age` contains the **bare 32-byte Ed25519 seed** (not the `minion-ed25519-seed-v1:` key-file representation; exactly 32 bytes, any other length is a defect) encrypted with the **age** format using a single **scrypt** recipient (binary, not armored, mode 0600). The Hub records its SHA-256 in `root_file_sha256` (section 7). The file is the only on-disk copy of the root. It is written only by D1 (temporary file, sync, rename), so it never exists incomplete.

### 10.2 Key derivation

- **KDF: age scrypt** (scrypt with a random 16-byte salt in the age header, `r = 8`, `p = 1`). **Work factor 18** (`N = 2^18`: about 256 MiB of memory and about one second on a current server CPU), the age default. Files are written with work factor 18 (`SetWorkFactor(18)`).
- When reading, the Hub accepts **only work factor 18** (`SetMaxWorkFactor(18)`, as in `internal/identity/sealedroot.go`) and treats a file at any other factor as unreadable (generic failure, 10.5). A later release that changes the factor must define its own migration.
- At most one unseal runs at a time (the rotation mutex), so the memory cost cannot be multiplied by parallel requests.

### 10.3 Passphrase rules

- **Minimum length 14 characters** (Unicode code points; the page counts them). Maximum 1,024 bytes. The page recommends five or more random words, or 20 or more random characters, and says that the passphrase protects against an attacker with unlimited offline guesses, so length matters more than looks.
- It is used byte for byte as typed (UTF-8, no normalization). The documentation warns that a passphrase with accented or composed characters may be entered differently on another keyboard, and recommends plain ASCII words.
- It must be entered twice (set, change, rotate). A change or rotation must give a passphrase that differs from the current one. It is refused if it equals the administrator's login password where the Hub can check that (local password accounts).
- The Hub does not estimate strength beyond these rules; a long weak phrase passes. The documentation says so.

### 10.4 Handling: never stored, never logged, wiped

- **Never stored.** Not in a file, the database, an environment variable, a keyring or a cache between operations. Each operation asks again.
- **Never logged or transmitted elsewhere.** Request and response bodies of the four operations are excluded from access logs and tracing; audit events and error messages never contain it (8.5); it is accepted only in the body of the operation request (UI: over TLS to the Hub; command: over the local Unix socket) and nowhere else; it is not accepted in a URL, header, argument or environment.
- **Memory wipe, best effort.** The Hub reads the passphrase into a byte slice, passes it to the key derivation, and zeroes the slice, the decrypted key-file plaintext, the seeds **and the complete private storage of every signer** as soon as the signing is done, in a deferred cleanup that also runs on error and panic. This is **best effort and not a guarantee**: the age library takes the passphrase as a Go string, which cannot be zeroed and may be copied by the garbage collector; the HTTP stack may buffer the request body; the operating system may have paged memory out. The Hub marks its process non-dumpable (no core dumps) and locks the pages of the seed buffers where the system allows, and the documentation advises encrypted or disabled swap. The honest consequence is in section 2: an attacker inside the Hub while the passphrase is typed can read it.
- **Operation-scoped destroyable signer (design decision).** The released `identity.KeyFromSeed` (`internal/identity/keys.go`, near line 54) builds a separate Ed25519 private key (64 bytes: seed and public key) and keeps it inside a closure, so zeroing the input seed leaves a usable signing key in memory that nobody can wipe. The root and every new key therefore never go through it. A new type in `internal/identity` (`ScopedSigner`) is created from the seed, **owns** its 64-byte private storage in a field it can reach, and has `Public()`, `Sign(purpose, data)` (the same rule as `identity.Sign`: prefix applied once) and `Destroy()`. `Destroy` overwrites the whole private storage and its copy of the seed with zeros, is idempotent, and makes every later `Sign` return an error. The decrypted key-file buffer (read from the age reader into a slice that the Hub owns, not into a string) is zeroed as soon as the seed has been copied into the signer, and the seed copy is zeroed as soon as the signer is built. Each operation creates its signers, and a single deferred function destroys all signers and zeroes all buffers on **every exit**: success, error, early return and panic. The signer does not leave the operation: it is not stored in the registry or in any struct that outlives the call. This remains best effort for the reasons above (the Go runtime may have copied stack or heap memory before it was zeroed). The plain operational key, which the Hub needs at run time, is a normal long-lived key and is not covered by this rule.
- **Terminal.** The command reads the passphrase without echo and zeroes its own buffer; it never prints it.

### 10.5 Failure messages that do not leak

A wrong passphrase, a damaged file, a file whose hash differs, an unsupported work factor and a file that fails authentication all give **the same answer**: code `passphrase_invalid` (HTTP 403), text "The passphrase was not accepted." The answer is the same whether the account exists, whether the file is intact, and how many characters were right. The server log carries only the generic event `hub_identity.unseal_failed` with the count. **Timing policy (narrowed guarantee).** The failure cases differ in how far the operation gets: a hash mismatch fails before decryption, and age rejects a malformed header or an unsupported work factor before any scrypt. To keep the time from telling the classes apart without ever running work the Hub does not support: (1) a file that is accepted for reading (hash matches, header valid, work factor 18) is decrypted, and a wrong passphrase therefore takes the time of a factor-18 derivation; (2) for every **early failure** (hash mismatch, malformed header, work factor other than 18, truncated file) the Hub runs one **bounded dummy derivation**: scrypt at the current work factor (18) over the typed passphrase with a fixed dummy salt, then answers; it never runs the file's own factor, and never more than one derivation. (3) Since the Hub writes and accepts only factor 18, all failure classes take the time of one factor-18 derivation, within a tolerance; the documentation states that the guarantee is **equal timing at work factor 18**. Network jitter and the cost of the checks before the derivation are not equalized.

A lockout answers "Too many attempts. Try again after TIME." (code `rate_limited`) and does not run the key derivation. Missing authorization, a stale re-authentication and a bad CSRF token are answered before and separately (`forbidden`, `reauth_required`) and never touch the failure counter.

### 10.6 Rate limit and lockout

Two independent scopes, each with a persistent failure counter and lock time in the database (they survive restarts, so restarting the Hub is not a way around them): the **web scope** (UI and REST) and the **local scope** (the commands over the Unix socket on the Hub host). The checks of 8.1 run first; only a request that passed them, and is not locked, reaches the derivation.

**Exact transitions** (per scope; `f` = failure counter, `L` = locked-until time):
- **Locked** (`now < L`): the request is answered `rate_limited` without running the derivation. `f` and `L` are **not** changed, so a locked scope is never extended by further attempts, and a correct passphrase during the lock is also refused.
- **Failed passphrase** (not locked, derivation or file check failed): `f = f + 1`. If `f` is a multiple of 5, then `k = f / 5` and `L = now + min(15 minutes * 2^(k-1), 4 hours)` (15, 30, 60, 120, 240 minutes, then 240). Otherwise `L` is unchanged.
- **Successful unseal:** `f = 0`, `L = 0`.
- **Lock expiry** (`now >= L`) does not reset `f`: the next failure continues the count, so after the first lock the sixth failure does not lock and the tenth locks for 30 minutes.
- Failures count only when the request passed authorization, re-authentication, CSRF, transport, the hourly allowance of its scope and the state check. A forbidden, stale or forged request never counts. The counter update and its audit row (8.5) are one transaction.

**What this bounds.** One lock interval is at most 4 hours and a scope cannot try more than 5 guesses per interval. It does **not** bound repeated denial: an administrator who is freshly authenticated again and again (the attacker holds the administrator credentials, not only a stolen session) but does not know the root passphrase can fail five guesses after every lock, and keep the **web scope** locked for as long as the attack lasts. A stolen session alone cannot do this for long, because its freshness ends 5 minutes after the last real authentication, before even the first 15-minute lock has ended; a non-administrator is rejected before counting.

**Local-owner recovery path (design decision).** The owner who is at the Hub host uses the commands, which have their own counter and lock (same transitions, own columns), so a web lockout never blocks them. The local scope needs access to the Hub's 0600 socket, that is the Hub's operating-system user, which is the same trust as the data directory; it can only be locked by someone who already has that access. The owner may also stop the Hub, and the commands keep the failure counters in the database, so a restart does not reset them. The local scope has the same 5-guess limit, so this path does not give an attacker with a data-directory copy anything new (that attacker guesses offline anyway, and the work factor is what limits that).

**Hourly allowance per scope.** Each scope has its own allowance of 10 attempts per hour (web and local are independent). A request refused with `rate_limited` because of a lock consumes no allowance; an attempt that reaches the key derivation consumes one unit, right or wrong. The allowance is checked before the lock and the derivation as in 8.1 item 6 and does not change `f` or `L`.

This limits only online guessing; it does nothing against an attacker who holds a copy of the file (that is what the work factor and the minimum length are for).

### 10.7 Forgotten passphrase

There is **no recovery, by design**: no escrow, no backdoor, no reset question, no second key. The sealed root cannot be opened without it. The Hub keeps serving until the certificate expires; after that the way back is a new Hub identity (a new data directory) and re-enrollment of all Workers. The page and `docs/security.md` say this before the owner sets the passphrase, and the owner is advised to keep the passphrase in a password manager or on paper in a different place from the Hub and its backups.

## 11. Protocol 3.0, handshake and expiry

### 11.1 Version (design decision)

The wire protocol becomes **3.0**. The handshake changes meaning (the Hub is authenticated through a certified key, not through the pinned key itself), which is a major change under the AD-4 rule. A 0.7 Hub and its Workers **upgrade together**; negotiation accepts only 3.x; there is no 2.x fallback and no downgrade, and a 2.0 Worker gets `proto_incompatible` and keeps retrying with backoff until it is upgraded. The signed release manifest carries `protocol_range` `3.0..3.0`. A minor bump (2.1) negotiated with 2.0 Workers was considered and rejected: a 2.0 Worker would have to accept a connection whose Hub signs with a key that its pin does not name, which is exactly the downgrade this design closes. Every field that 3.0 adds to the handshake is mandatory; a missing or malformed value is rejected (`invalid_argument`), nothing is defaulted. The transcript label `minion-hs-v1` stays: the protocol version in the hello, which is hashed, already separates the generations.

### 11.2 Frames

1. **Worker `hello`**, unchanged in its fields: version range, ops and features, `worker_pub`, ephemeral X25519 `eph_w`, a 32-byte nonce, `mode` (`connect`, `enroll_invite`, `pair_code`), its name and, in `pair_code` mode, the public pairing id.
2. **Hub `hello`** `{type, version, hub_pub, hub_cert, eph_h, nonce, chain?}`: `version` is `3.0`; `hub_pub` is the **root** public key and must equal `cert.root_pub`; `hub_cert` is the 153-byte certificate in base64url, mandatory in every mode; `chain` only in `connect` mode. The Hub sends it only after admission and negotiation succeeded, and only with a certificate whose `not_after` is in the future (else `hub_cert_expired`).
3. **`transcript_hash`** = SHA-256 of `"minion-hs-v1"`, then the length-prefixed Worker hello as sent, then the same for the Hub hello as sent. The certificate is in the Hub hello, so it is bound into the transcript before any PAKE and any signature.
4. **The Worker validates the Hub hello in this order** and stops at the first failure with nothing written to disk (steps a to d are the same in all modes, e differs) (N2):
   - a. *Shape*: lengths of `hub_pub`, `eph_h`, `nonce` (32 each); `version` in range; `hub_cert` present and 153 bytes; a chain only in `connect`.
   - b. *Root*: `connect`: resolve the chain from the stored pin into a **temporary candidate root** (`VerifyChain`; the candidate is the pin when the chain is empty), `hub_pub` must equal it (`ErrPinMismatch`). `enroll_invite`: the fingerprint of `hub_pub` must equal the invitation's (the root, never the operational key). `pair_code`: the root is only a claim until pairing completed and is not pinned; it is the candidate for the next checks, **and if a `pair_resume` record exists (section 12.2) it must equal the root stored in that record** (`resume_root_mismatch`: the Worker closes before `sig_worker`, keeps the record and the code).
   - c. *Certificate*: structural validation, `cert.root_pub == hub_pub == candidate`, signature under the candidate.
   - d. *Window*: the Worker reads wall clock `now_ms` and, back to back, the monotonic clock `mono0`. It accepts iff `not_before - 3,600,000 <= now_ms <= not_after` (checked; one hour before `not_before`, nothing after `not_after`). A certificate accepted at exactly `now_ms == not_after` admits no operation (its deadline is `mono0` and the `>=` rule closes it).
   - e. *Serial scope (verdict deferred)*: `connect`: if the candidate equals the stored root, compare with `max_serial` and `cert_sha256` (`cert_serial_too_low`, `cert_serial_conflict`); for a different, verified root the scope is new and `max_serial` counts as 0. `enroll_invite`: no scope; any valid serial is the first. `pair_code` with a `pair_resume` record: the record's serial and hash are the scope, with the same two verdicts; without a record any valid serial is the first. The Worker keeps the verdict and continues.
5. **`sig_hub`**: purpose `hs-hub` over `transcript_hash`, signed with the **operational key**; the Worker verifies with `cert.op_pub`, never with `hub_pub`. In `pair_code` mode it comes after the CPace exchange. If `sig_hub` is invalid: `hub_sig_invalid`, close, verdict dropped. If valid and a verdict is pending: close **without `sig_worker`**, report locally with the command of section 6; nothing is written.
6. **`sig_worker`** (purpose `hs-worker`) only now, and only if no verdict is pending. In `pair_code` mode the `pair_resume` record is durable before this frame is sent (section 12.2).
7. **Key schedule** unchanged: HKDF-SHA256 over X25519(eph_w, eph_h), `transcript_hash` as salt, plus the CPace output in `pair_code` mode; two directional ChaCha20-Poly1305 keys.
8. **Commit (Worker)**, one SQLite transaction under the enrollment-generation guard, by mode:
   - `connect`: after step 7 and **before any operation is admitted**: the pin (root and chain position, if changed), `max_serial = max(max_serial, cert.serial)` and `cert_sha256` for the highest serial (a new root resets both first). A commit is needed also when only the serial rose.
   - `enroll_invite` and `pair_code`: the enrollment is **uncommitted until a valid `welcome` arrived inside the channel**. Until then the candidate root, chain position 0, serial and certificate hash are in memory (and, for `pair_code`, in the `pair_resume` record, which `connect` mode ignores: it is not an enrollment and not a pin). On `welcome`, in one transaction: the enrollment, the root as pin, chain position 0, `max_serial` (the higher of the record's and this session's), `cert_sha256` of the highest, and the deletion of the `pair_resume` record; success is reported after the commit. Anything earlier (rejected invitation, wrong or expired code, error frame, closed connection, crash) leaves no pin, root, serial or enrollment. Recovery of a Hub-committed enrollment whose Worker commit did not happen is section 12.
9. Everything else, including the invitation secret, `welcome` and revoke, travels inside the channel; the invitation secret is sent only after step 7.

**Precedence** when several conditions hold, the earliest wins: shape (`cert_missing`/`cert_malformed`), root (`cert_root_mismatch`, `resume_root_mismatch`), signature (`cert_bad_signature`), window (`cert_not_yet_valid`, `cert_expired`), in `pair_code` the CPace tag (`pake_confirm_invalid`) and confirmation signature (`pake_sig_invalid`), `hub_sig_invalid`, then `cert_serial_too_low` / `cert_serial_conflict`. There is no code on the wire for these reasons; the Worker closes the connection and records the reason in its status and log (transport error codes: `invalid_argument` for `cert_missing` and `cert_malformed`, `pairing_code_invalid` for `pake_confirm_invalid`, `unauthenticated` for all others). Only `hub_cert_expired` (HTTP 503 with `Retry-After`) is a new answer on the wire. There are **no in-band floor reports** of any kind.

### 11.3 Worker-enforced expiry (N3)

- At step 4d the Worker records `expiry_wall = not_after` and `deadline_mono = mono0 + (not_after - now_ms)` for this connection. No allowance is added after `not_after`.
- The session is over when `now_wall >= expiry_wall` **or** `mono_now >= deadline_mono` (equal counts as expired on both clocks, the same rule as the Hub's `now >= not_after`; the wall-clock test is independent of the monotonic deadline, so a wall clock that jumps to exactly `not_after` before the monotonic deadline closes the session). Both clocks are read at each of: a monotonic timer set to the deadline and every keepalive tick (30 s); when a stream is accepted, either direction; **after the request is decoded and immediately before the operation is admitted** (op admission recheck); and immediately before a `revoke` is applied (a revoke at or after the cut-off is not applied, the session closes, the pairing stays). A wall clock moved backwards cannot extend the session beyond the monotonic deadline; after a sleep, the first check sees the wall clock.
- In-flight work: on expiry no new operation is admitted; a read in flight fails with `connection_lost`; a write that already started completes locally and the Hub reports its outcome `unknown`, never replayed. The Hub also closes every session at `not_after`.
- Expiry never touches the enrollment or the pin. The connector's injected clock provides `Wall()` and `Mono()` so the cases are testable.

## 12. Enrollment, pairing and recovery

### 12.1 Invitations

The format is unchanged: `mnk_<root fingerprint>.<secret>`; the secret is 32 random bytes in lowercase base32. Keys created by a 0.6 Hub stay valid because the root is the old identity key, unchanged, only sealed (section 9.7). The Worker sends the secret only after the certificate, window and `sig_hub` are verified, and commits only after `welcome` (step 8). Enrollment is already idempotent per `worker_pub` (the Hub's `EnrollWithInvitation` returns the existing Worker for the same key without consuming another use), so a crash between `welcome` and the Worker's commit is repaired by repeating the enrollment. Re-issuing the certificate never revokes invitations; a master-key rotation does.

### 12.2 Pairing: idempotent per (pairing code, Worker key) (design decision)

Today (`internal/hub/workers/pairing.go`) a Hub commit that the Worker never records leaves the Worker stuck: `Claim` refuses a used code (about line 476, `PairingCodeUsed`), `loadRow` refuses a used pairing id (about line 397), `create` answers `already_paired` for a known Worker key (about line 529), and `CompletePairing` answers `ErrPairingCodeUsed` (about line 560). The Worker also retires its code after any exposed connection that did not pair (`classify` in `internal/worker/agent/pair.go`, about line 113), so after a lost `welcome` or a crash it would show a different code.

**Hub side: the pairing commit is recorded.** The existing table `used_pairing_codes` (digest, `used_at`) is extended by the forward-only migration with `pairing_id` TEXT, `worker_pub` BLOB, `worker_id` TEXT, `owner_id` TEXT, `expires_at` INTEGER (the code's expiry, copied from the pending row) and `resume_attempts` INTEGER NOT NULL DEFAULT 0. `CompletePairing` writes them in the same transaction that inserts the Worker. Rows from before the migration have `expires_at` NULL and never resume (today's behaviour). **The stored digest is weak protection:** a pairing code has few unknown bits (about 20), so anyone who can read the database can recover it from the digest by guessing. Resume therefore never relies on the digest's secrecy; it relies on the same Worker key, the commit's owner, the expiry and the attempt counter below.

**Worker side: the code and the authenticated Hub identity survive (design decision).** The Pairer persists a record in the Worker state (new table `pair_resume`, forward-only migration; the state directory is private to the Worker's user and the code is already printed on its console): `{code, pairing_id, expires_at, root_pub, chain_position 0, serial, cert_sha256}`, where the last four are the **authenticated candidate root and its certificate ratchet** from this very handshake. The record is written, with a durable commit flushed to disk, at the moment the Hub is authenticated (CPace confirmation tag and signature, certificate and `sig_hub` verified) and **before** the Worker sends `sig_worker`. The Hub cannot create the Worker before it has received `sig_worker`, so the record always precedes any Hub commit. The record is deleted in the same transaction as the enrollment commit, at expiry, and by `minion worker reset`. **Abandoning the identity retires the old code:** a Worker that is reset, or whose record has expired, deletes the record and shows a new code; until then it refuses any Hub whose root differs from the record (section 11.2 step 4b) and keeps the record. This closes identity substitution on resume: a peer that learned the code could pass CPace, but cannot present another root, and cannot lower the certificate serial the record holds.

`classify` changes: a connection that ends after the Hub was authenticated and before `welcome` keeps the code and reuses it until expiry. This is safe against the interceptor concern that motivated the retirement (one guess per connection), because only a peer that knows the code can produce the Hub confirmation: the rule never keeps a code after an unauthenticated peer. After a restart the Pairer reads an unexpired record, reuses the code, prints "Resuming pairing: enter the same code again in the Hub (Add worker)", and sends the same pairing id.

**Resume at the Hub.**
1. *Hello.* In `loadRow`, a pairing id whose row is `used` is refused as today **unless** a `used_pairing_codes` row exists for that `pairing_id` with `worker_pub` equal to the hello's key and `expires_at > now`. Then the Worker waits as for a pending code, with a resume ticket and no new pending row.
2. *Claim.* The owner types the same code. In `Claim`, the used-code check moves behind the live-entry lookup: a used code is accepted only if the live entry carries a resume ticket whose digest equals the typed code's digest **and** the claimant is the commit's `owner_id`; otherwise the message is today's "this code was already used". Wrong typed codes are counted in `resume_attempts` (five at most) instead of the pending row.
3. *Fresh CPace.* The handshake runs normally with the typed code (the Hub holds no password, only the digest). Nothing about the first run is reused; the Worker applies the root and serial checks of its record (11.2 steps 4b and 4e).
4. *Create.* After the tombstone check (a removed Worker still gets `revoked`), `create` with a resume ticket loads the Worker row named by `worker_id` and returns it as the existing enrollment: no insert, no new name suffix, no new digest, audit `worker.pair_resume`, and `welcome` carries the current row (including its pending-approval state). Without a ticket, a known Worker key still gets `already_paired`.
5. *Other keys.* A different key with the same code finds no matching commit row: the hello is refused as today. The same key with a **different** code and no repair window (12.3) gets `already_paired`.

Cases covered: **(a) lost welcome** (the Hub committed and sent it, the connection died): the Worker kept its record and the code, resumes as above. **(b) crash after a valid welcome and before the Worker's commit**: the record is on disk, same path. **(c) Hub crash before its commit**: no commit row, the pending row is still pending, the owner claims again as today. **(d) Hub committed, Hub crashed before sending welcome**: same as (a). **(e) a different Hub identity answers the resume**: refused by the Worker, record kept.

### 12.3 After code expiry: owner re-issue (design decision)

If the code lifetime (10 minutes) passes before the retry, the Worker is stuck between the Hub commit and its own: it has no pin, the Hub has a Worker row. Recovery is by the owner in the Hub:

- **Operation** `worker_pairing_reissue` (CLI `minion hub worker repair-pairing WORKER`; Workers page button "Re-issue pairing" shown for a Worker whose `first_connected_at` is empty and whose code has expired). Allowed for the Worker's owner and for administrators. Eligibility: the Worker has a live row and no tombstone (released removal deletes the live Worker row and writes a separate tombstone, so a removed Worker has no live row), and has **never completed a connect handshake** (new column `workers.first_connected_at`, set when a `connect` handshake registers; backfilled with `created_at` for rows that exist at migration, so no existing Worker is eligible); otherwise `conflict`.
- **Effect:** sets `workers.repair_until = now + 10 minutes` (new column, default 0) and audits `worker.pairing_reissue`. Nothing else changes.
- **Completion:** the Worker, which has no state to keep, simply shows a new code as in any pairing (`classify` renews it at expiry; a user may also rerun `minion worker pair`). The owner (or an administrator) enters the new code. In `create`, when the Worker key is known, `repair_until > now`, `first_connected_at` is empty and the claimant is the row's owner or an administrator, a repair transaction marks the new pending row used, records a new `used_pairing_codes` row (with the commit fields), clears `repair_until`, and returns the existing row; otherwise `already_paired` as today. The Worker keeps the same Worker id, name and approval state.
- **Atomic eligibility (design decision).** Each eligibility check and the write it guards are one transaction with a conditional update: setting `repair_until` is `UPDATE workers SET repair_until = ? WHERE id = ? AND first_connected_at IS NULL AND NOT EXISTS (<a tombstone for this Worker key in the existing tombstone table>)` inside the transaction, which must change exactly one row (a removed Worker has no live row, so the update matches nothing); the repair in `create` clears `repair_until` with `WHERE repair_until > now AND first_connected_at IS NULL` in the same transaction as the used-row and commit-row writes. A connect handshake that sets `first_connected_at` at the same moment therefore wins or loses cleanly; no check is read in one transaction and acted on in another.
- If the Worker key itself was lost, there is no recovery of that row: the owner removes it and enrolls the new key.
- The Worker's error text for `already_paired` after expiry says: "The Hub already knows this Worker key. Ask the owner to use Re-issue pairing for this Worker."

### 12.4 Revoke signer (AD-9)

A `revoke` is signed with purpose `revoke` over the `transcript_hash` of that very connection by the **operational key whose certificate was presented in that handshake**. The Worker verifies it with the `cert.op_pub` it validated in that handshake and keeps for the session; a revoke signed by the root, a previous operational key or another connection's key is ignored with a warning, nothing is deleted. The Hub takes the signer once per connection (key and certificate as one pair, with the generation of 9.6) into the connection's registry entry; the live revoke and the tombstone answer at reconnect both sign with that entry's key. A revoke needs no root and no passphrase. A removed Worker that was offline across a re-issue is revoked at its first handshake afterwards. Pairing never ends by timer; a Worker wipes its pairing only on a signed revoke. The expiry of the Hub certificate never unpairs a Worker.

### 12.5 Self-retirement carries the certificate ratchet (design decision)

Released code replaces a Worker identity in `internal/worker/agent/pair.go` (near line 815): it adds the old key to the `RetiredStore` and then calls `Wipe`, which deletes the enrollment row. With section 6 the row also holds the root-scoped ratchet (`max_serial`, `cert_sha256`), so a wipe would reset it and a stale certificate (still inside its window) could answer `not_enrolled` on the retirement connection of `internal/worker/agent/pair_retire.go` (near lines 82 and 398) and make the Worker discard the pending revocation.

1. **Carry before wipe.** `RetiredIdentity` and `retiredMeta` gain `max_serial` (uint64) and `cert_sha256` (32 bytes or absent) next to `hub_pub` and `pin_seq`, and `retiredMeta.version` becomes 2. `RetiredStore.Add` writes them from the enrollment row **in the same private metadata file** as the key, durably (D1 and a directory sync), and only then does the caller `Wipe`. An `Add` that fails aborts the replacement before the wipe, as today.
2. **Validate on every retirement connection.** The retirement handshake runs steps a to d of 11.2 with the retired pin: the certificate chains to the pinned root (or follows the chain transition as in 11.2), its window is current, `serial >= max_serial`, and with `serial == max_serial` the hash equals `cert_sha256`. A failure is the same refusal as on a normal connection (`cert_serial_too_low`, `cert_serial_conflict`); the retirement stays pending and nothing is discarded.
3. **Advance durably.** After `sig_hub` verified and **before** the Worker acts on `revoke`, `not_enrolled` or `welcome`, a higher serial (or the first hash at an equal serial) is written to the retired metadata file (temporary file, sync, rename, directory sync). Only a durable write permits the result `already_revoked` or `not_enrolled` to retire the entry. A failed write ends the connection with the entry kept.
4. **Only a validated connection can answer `not_enrolled`.** A `not_enrolled` frame counts only when the handshake above passed; a stale operational certificate cannot produce it.
5. **Migration of existing retired metadata.** Version-1 files have no ratchet. On load they are read as `max_serial = 0` with `ratchet_seeded = false`. The first validated retirement connection seeds the ratchet (step 3) but may only complete through a signed `revoke` (`already_revoked`) or `welcome`; a `not_enrolled` on that first connection leaves the entry pending, and a later validated connection with `serial >= seeded serial` may retire it. The file is rewritten as version 2 at the seed. Residual risk, stated: until the seed, a version-1 entry has no memory of the root's earlier serials.

## 13. Backup and restore

- **Contents per bootstrap state (design decision for the list; the archive format and age encryption are the 0.6.x backup work).** The state is read from the database copy (`root_sealed`, `current_cert`), never from which files happen to exist. The archive always holds the database snapshot (it holds the certificate state), `data.key` and TLS material, plus exactly the identity files of that state:

  | State of the copy | Identity files in the archive | Operational key |
  | --- | --- | --- |
  | **B0** (no `hub_identity` row) | none | none |
  | **B1** (`root_sealed = 0`) | the plain `identity.key` (as 0.6 does; stated in the manifest and in the backup guide: the root is plain inside the archive) | none: there is no certificate and no `op.key` yet |
  | **B2** (`root_sealed = 1`, no certificate) | the sealed root `root.key.age` | none |
  | **B3** (`root_sealed = 1`, certificate set) | the sealed root `root.key.age` | `op.key` |

  There is no mode that leaves a recorded root out. The archive is itself age-encrypted as in 0.6.x, which is a second layer, not a replacement for the sealed root. The manifest records the state (`identity_state`: `none`, `plain`, `sealed_no_cert`, `established`), the root fingerprint and the number of transition records in the copy (used by the restore warning below).
- **Snapshot rule (the only definition; design decision).** The snapshot takes the database copy first, then selects the files that belong to that copy, each independently: (1) the **root file**: in B1 the `identity.key` whose public key equals the recorded root (as `snapshotWithIdentity` in `internal/hub/store/backup.go`, near line 337, does today); in B2 and B3 the **sealed root**: of `root.key.age` and `root.key.age.next` the one whose SHA-256 equals the `root_file_sha256` recorded in the copy (the hash replaces the public key because the file cannot be opened without the passphrase); (2) **only in B3** the **operational key**: the key whose public key equals the copy's `C.op_pub`, searched in `op.key` and `op.key.next`, because the state may have moved on since the copy. If a selected file is not found (including a B1 copy whose plain file was just sealed and removed) the whole snapshot is repeated, at most five times (`maxSnapshotAttempts`); then the backup fails with an error naming the facts. The archive stores the files under normalised names `identity.key`, `root.key.age` and `op.key`. A snapshot taken at A2 or A3, or between X2 and X4, restores as a consistent set.
- **The manifest** gets `format` 2 (design decision). Format-1 archives (0.6.x) are classified **by their migrated database and validated files**, not by the format number: no recorded Hub identity and no key file gives **B0**; a recorded identity with a matching plaintext `identity.key` gives **B1** (the plain root of a migrating database, section 9.7) **without requiring `op.key` or a certificate**; a recorded identity without its key file is **rejected**, as released behaviour (`internal/hub/store/backup.go`, near lines 113-116 and 776-783).
- **Restore is two phases (design decision).** The 0.6.x restore verifies the staged files against the archive manifest (`copyStaged` in `backup.go`, near line 897, compares names, sizes and hashes). Transforming a staged file changes its hash, so the phases are separate:
  1. *Verify the immutable archive.* Decrypt and unpack into a private temporary directory; verify every entry against the manifest; reject unknown names. The archive, its manifest and the verified files are not modified afterwards.
  2. *Migrate and transform the staged copy* (Hub stopped, still in the private directory): migrate a format-1 database; checkpoint and close SQLite so no `-wal` or `-shm` file remains; run the integrity checks; **validate the identity per state of the restored database** (B0: the archive carries no identity file and none is expected; B1, including a format-1 archive with a recorded identity: the public key of `identity.key` equals the recorded root, and no operational key or certificate is required or installed; B2: the SHA-256 of `root.key.age` equals the recorded `root_file_sha256` and no operational key is required; B3: the same, and the operational key matches `C.op_pub`). A state not listed, or an archive whose files do not fit the state, is refused with the error naming the facts. Then build a **trusted internal install plan**: the list of final names, sizes and SHA-256 values computed now, in this process, from the transformed files. The installation (`installRename` near line 1249, with its rollback) verifies against that plan and never against the archive manifest.
- **Restore rules.** Both phases complete before the destination is touched. The archive must contain exactly the identity files of its state (table above; a format-1 archive is classified as B0 or B1 as above); a missing or non-matching root file is rejected with today's error. A restore **does not issue a certificate** and needs no passphrase (design decision): it installs the backed-up state, so the restored Hub is in the state of the backup. If its certificate has expired or Workers refuse its serial, the owner re-issues (section 8; for refusal use the recovery command of section 6).
- **Serial rollback versus root rollback (design decision).** Two different restores must not be confused. A **serial rollback** restores a backup from the same root with an older serial state; the recovery is the serial floor of section 6, because a Worker accepts any certificate under its pinned root with a high enough serial. A **root rollback** restores a backup made **before a master-key rotation**: its sealed root is the retired root, while Workers have followed the chain to the new root and pinned it. Re-issuing under the retired root cannot repair this: released `VerifyChain` (`internal/identity/chain.go`, near line 136) only follows transitions **forward** from the pinned root, so a Worker pinned to the new root rejects the retired root (`ErrPinMismatch`), and no serial floor changes that. The restore therefore compares the transition-record count and the root fingerprint of the manifest with what it can know and prints, at restore time, "this backup holds a root that may have been rotated away; Workers that followed the rotation will refuse this Hub" whenever the backup is older than the owner's last rotation (the owner confirms the date; the Hub cannot know what happened after the backup). Recovery paths: (1) **restore a backup made after the rotation** (it holds the new sealed root and the transition record); (2) if no post-rotation backup exists, the new root is lost with it, and the only way back is **out-of-band re-pinning**: every affected Worker is reset (`minion worker reset`) and enrolled again with a new invitation under the restored root (the pairings and Worker identities are re-created; a Worker that has not yet followed the rotation is unaffected). The documentation of the backup guide states both paths, and states that the first backup after every master-key rotation is mandatory.
- **Which passphrase.** The backup holds the sealed root of its own time. After a passphrase change, an older backup still opens with the **old** passphrase; after a master-key rotation an older backup holds the retired root. The documentation says so, and the owner keeps the passphrase of each backup generation in mind or discards old backups.
- **Disclosure of a backup (N4; to be written into `docs/security.md` and the backup guide).** A disclosed backup hands over (1) the **operational key**: re-issue the certificate at once; the thief's key is then useless to every Worker that sees the new serial and, to the others, until the old `not_after`; (2) the **sealed root**: safe if the passphrase is strong and unchanged in the thief's reach; if the passphrase is weak or may be known, treat it as a root compromise (section 2, second row) and plan the new identity; **changing the passphrase does not help** against a thief who already holds the file, because the old file opens with the old passphrase, and a rotation helps only for the future. Backups made by 0.6.x hold the **plain** identity key: a disclosure of one is a root compromise (section 14 recommends one rotation after the upgrade for this reason).

## 14. Migration from 0.6.x (design decision)

0.6.2 has a plain `identity.key`, a `hub_identity` row (`pub`, `fingerprint`, `created_at`), the transition chain, and a Worker `hub_enrollment` pin. **The 0.7 Hub and all Workers upgrade together to protocol 3.0** (section 11.1); there is no mixed operation. Nothing needs re-enrollment: pins stay valid and every `mnk_` invitation keeps working, because the root is the old identity key unchanged.

Hub, first 0.7 start, before the first Worker listener opens (Go code after the forward-only SQL migration; idempotent, so a crash at any point is repaired by the next start):
1. Complete or discard a pending `identity.key.next` with the existing 0.6 rotation recovery; the result is `identity.key`.
2. The migration sets `root_sealed = 0` and `migrated_from_06 = 1`. `identity.key` stays where it is: the Hub is in state B1 (section 9.7). It does not create `op.key` and does not create a certificate: the first certificate must carry a fresh key (section 4), and signing needs the root, which the owner seals first.
3. **The Hub does not serve Workers until the owner has set the passphrase.** The web UI starts and shows the banner "Set the Hub passphrase"; the command `minion hub identity set-passphrase` does the same. The owner types the passphrase twice; the Hub seals the identity key into `root.key.age`, removes the plain file and issues the first certificate (180 days). Workers on 3.0 then connect with the unchanged pin. This is a one-time interruption that the owner causes and ends; it is announced in the release notes.
4. A recorded identity whose key file is missing is **not** regenerated (fail closed, as released `identity.go`).

**Recommended: one master-key rotation after the upgrade.** The pre-0.7 backups, and any other copy of the old `identity.key`, hold the root in plain form, and sealing the file on the Hub does not change them. The page therefore shows the banner "Rotate the master key" while `migrated_from_06 = 1`. Order for the owner: upgrade the Hub, set the passphrase, upgrade the Workers and let them connect (they pin the old root), then rotate (section 8.2): the Workers follow the chain at their next connect and pin the new root; afterwards a stolen pre-0.7 backup no longer impersonates the Hub to a Worker that has followed. State of the residual risk: a Worker that has not yet followed, and a Hub whose old key was already stolen before the rotation, are not protected by it (a thief with the old root can sign a competing transition); the rotation is a hygiene step for the future, not a repair. Rotation revokes all invitations, so unused `mnk_` keys must be created again.

Worker, first 0.7 start: forward migration adds `max_serial = 0`, `cert_sha256 = NULL` and the `pair_resume` table. The first successful `connect` against the upgraded Hub accepts the certificate under the pin and commits the serial.

**Upgrade procedure caveat.** 0.7.0 declares protocol range `3.0..3.0` against 0.6.2's `2.0..2.0`. What 0.6.2 actually does: `minion update` contains a guard (`checkProtocol` in `internal/version/update.go`, near line 358, called through `hubRange` in `internal/cli/update.go`, near line 261) that would refuse a protocol-disjoint release, but its source of the connected Hub's range (`SetHubRange`) is **not wired in production**, so without the `--hub-proto-range` flag the 0.6.2 updater performs no protocol check and installs the release. What is intended: the guard refuses once the source is wired (a 0.6.x patch would be needed; open question 3). Either way the order is the same: take an encrypted backup of the 0.6.2 Hub; upgrade the Hub first (package or `bootstrap.sh`); set the passphrase; then upgrade each Worker. A Worker updated earlier reports `proto_incompatible` and retries with backoff until the Hub is upgraded. There is no database downgrade; the backup is the way back. A restore of a 0.6.x archive into 0.7 is supported (format 1, section 13).

## 15. Windows

`root.key.age`, `op.key` and their `.next` files follow the existing Windows rules for private files and replace-rename; the states of section 9 are the same. Overwriting the plain `identity.key` before unlinking is best effort on every file system (copy-on-write and SSD wear levelling may keep old blocks); the documentation says so. The Windows Worker remains a preview.

## 17. Test obligations

Each item is a named test; crash tests use injected failure points at the boundaries named in sections 9.3, 9.4 and 9.7, and error-injection tests use injected failures of `MakeDurable`, of the directory sync and of each rename.

**Certificate and files.** Golden vectors (positive, negative, extremes) read by encoder, parser and verifier; the default validity is 180 days and `--validity` applies to one issuance only.

**Re-issue is rotation.** Every issuance (first, re-issue) produces a different `op_pub`; **a stolen previous operational key cannot authenticate with any newly issued certificate** (the thief signing `sig_hub` with the old key under the new certificate fails `hub_sig_invalid`; presenting the old certificate to a Worker that has seen the new serial fails `cert_serial_too_low`; presenting it to a Worker that has not is accepted only until the old `not_after`, which the test asserts and then asserts refusal one millisecond after); the new certificate does not extend the old key's validity; all sessions close at each issuance.

**Serials.** Two allocations in one millisecond differ; re-issue raises the serial; `last_issued` is never lowered; a clock rollback with a durable database never repeats a serial; a floor above `now + 366 d` is refused without `--allow-far-floor`; property test over random operation sequences with injected crashes: within one database lineage no serial is allocated twice and none with two payloads. **Ordinary restore:** the restored Hub keeps the backed-up certificate, either every Worker connects or a Worker refuses with `cert_serial_too_low` or `cert_serial_conflict`, logs the documented command and `reissue --serial-floor N` repairs it (the test accepts both outcomes and asserts the second one fully). **Collision (separate):** a restored or forked issuance state allocates a serial equal to one a Worker holds with different bytes; the Worker refuses with `cert_serial_conflict` after a valid `sig_hub`, sends no `sig_worker` and no frame naming `max_serial`, logs the command, stores nothing; the command repairs it. A hostile client cannot change Hub serial state (there is no input).

**Activation, durability and recovery.** One test each for A1 to A5 (9.3), X1 to X5 and W1 to W4 (9.4) asserting the durable facts after the crash, the recovery action at start, and that the flow completes afterwards. Power loss: a database copy from before the commit combined with the files of after it (N removed; RN removed; the old passphrase still opens RK), and the case that D2 forbids is shown unreachable by an injected failure of the directory sync (the transaction is not started). Error injection: `MakeDurable` fails or the request is canceled between COMMIT and the checkpoint (the Hub keeps its previous pair, serves nothing new, keeps N and RN, refuses other changes with `conflict`, and the same command or the next start confirms and completes; a start with a failing `MakeDurable` refuses and keeps the files); a failed rename after a durable commit keeps serving, refuses the next change and succeeds after the retry; a key matching `C.op_pub` and a sealed file matching `root_file_sha256` are never deleted in any of these runs. **Master-key rotation:** sessions are closed and the generation rises; a stalled handshake that took the old root-and-key set fails at registration; the transition is signed by the old root and verifies; invitations are revoked; the new sealed file opens only with the new passphrase and the old passphrase opens nothing current. **Passphrase change:** no generation change, no session closes, no certificate change; the new passphrase opens RK and the old one does not.

**Bootstrap and setup (9.7).** **Set-passphrase eligibility:** accepted in B0 and B1; in B2 (and B3) the server answers `conflict` without reading or counting anything, the UI hides the action, the recorded sealed root is byte-identical afterwards, and a crafted request cannot replace it. A pristine data directory (B0) shows the setup, serves no Worker, and after **set passphrase** has a sealed root, row, first certificate and `op.key` and serves only at B3; a migrated 0.6 identity (B1) keeps its fingerprint and `mnk_` invitations, the plain file is gone after the setup and a sealed file with the same public key exists; one test for BS1 to BS5 asserting durable facts, recovery and completion (BS1 and BS2 remove an unrecorded RK, BS3 refuses to start and keeps **both** `identity.key` and the sealed file when `MakeDurable` fails, then a later successful confirmation allows the removal; BS4 removes the plain residue **only after** a confirmed commit, for RK and RN alike; a power loss between an unconfirmed commit and the removal never leaves a database that needs a deleted plaintext file); **fail closed:** a row with a missing sealed root or a missing `op.key`, and a row with a missing plain root, refuse to start, name the files, and no key is generated; plain residue while `root_sealed = 1` is removed; no Worker connection is accepted while `current_cert` is NULL.

**Passphrase handling (10).** The sealed file is a valid age scrypt file at work factor 18; a file at any other work factor (for example 17 or 19) is refused; the file holds exactly the 32-byte seed with the generic answer; a passphrase of 13 characters is refused and one of 14 accepted; a passphrase equal to the old one is refused on change and rotate; the passphrase equal to the administrator's login password is refused; **no leak:** with a wrong passphrase, a damaged file, a swapped file and an unsupported factor the response text, code and (within a tolerance) time are identical; the passphrase, any part of it and its length are absent from the response, the server log, the audit events, the access log and the panic output (a canary passphrase is searched in all of them after each operation, including a failing one and a panic injected between unseal and signing); the buffers handed to the key derivation, the decrypted key-file plaintext, the seed buffers **and the complete private storage of every `ScopedSigner`** (a test hook keeps the slice) are zero after the operation, also after an error and after a panic injected between unseal and signing; `Destroy` is idempotent and a `Sign` after `Destroy` returns an error; the root and new keys are never built with `KeyFromSeed`; a signer is not reachable from any structure that outlives the operation (this test does not claim anything about the string copy inside the age library); **timing:** every failure class of 10.5 (wrong passphrase, hash mismatch, damaged file, truncated file, malformed header, work factor 17 and 23) takes one factor-18 derivation within a stated tolerance, no early failure takes noticeably less, and no test file ever triggers a derivation at an unsupported factor (a counting hook on the KDF); the process is non-dumpable; the command refuses a non-terminal standard input and does not accept an argument, variable or file; nothing about the passphrase exists in the data directory after any operation.

**UI, REST and commands (8).** A non-administrator gets `forbidden` for each of the four operations and does not see the page's actions; a session authenticated more than 5 minutes ago gets `reauth_required` and nothing is changed or counted; a missing or wrong CSRF token, a foreign `Origin`, a `Sec-Fetch-Site: cross-site` request and a non-JSON content type are refused; plain HTTP gets `tls_required`; **transport:** a forged `X-Forwarded-Proto: https` from an untrusted peer is ignored, a remote browser reaching the Hub over plain HTTP through a reverse proxy on the loopback address is refused when that proxy is not a configured trusted proxy (the loopback peer address alone never qualifies), the same request through a trusted proxy that reports HTTPS is accepted, and the explicit local management listener is the only cleartext exception; **re-authentication:** `auth_at` and `auth_method` cannot be set by a request, a session from a silent SSO redirect has `auth_at = 0` and gets `reauth_required`, the OIDC re-authentication sends `max_age=0` and `prompt=login`, a callback with a missing or old `auth_time`, a different subject, an unknown or reused state or a provider that ignores `max_age` ends in `reauth_unavailable` with nothing updated, a re-authentication of one session does not make another session fresh, and the operation does not extend `auth_at`; **audit:** each state change has its audit row in the same transaction (a forced rollback leaves neither), lockout rows carry the counter and lock time, a CLI row carries the kernel-supplied `local:<uid>` actor, and the expiry events carry the system actor and are written once per UTC day across a restart; **lockout transitions** (per scope): failures 1 to 4 do not lock, the fifth locks for 15 minutes, the tenth for 30, then 60, 120, 240 and 240; attempts during a lock change neither counter nor lock time; the sixth failure after a lock expired does not lock; a success resets both; the lock survives a Hub restart; the web scope and the local command scope are independent (a web lockout does not block the commands, and the reverse), and a correct passphrase during the lock is also refused without running the key derivation; a repeatedly re-authenticated administrator can keep the web scope locked (the test documents this) while the commands still work; a stolen session loses freshness before the first lock ends; the eleventh operation within an hour is refused per scope; **allowances are independent:** an exhausted web allowance together with a web lock still permits a correct CLI operation, and the reverse; a request refused because of a lock consumes no allowance, while an attempt that reaches the KDF does; two simultaneous operations serialise; each action writes its audit event with actor and channel and no secret; the result is shown only after durability; the command works through the local socket and a socket with wrong permissions is refused.

**Expiry (8.4).** At the Worker, `now_wall == not_after` closes the session and admits no operation even when the monotonic deadline has not been reached (a wall-clock jump test independent of the monotonic clock); The banner, the Workers page countdown, the log line and the daily audit event appear at 30 days, the level rises at 7 days and none appears before 30; nothing renews a certificate by itself (a Hub left running past `not_after` does not issue); at `not_after` the Hub closes sessions and answers `hub_cert_expired` before the upgrade while the UI and commands work; after a re-issue Workers reconnect; a restart after expiry needs no passphrase.

**Backup snapshot.** A backup taken in each state of 9.3 and 9.4 and one taken while a state moves on between the database copy and the key read (retry path, bounded by five attempts, and the failure message when no file is found); **a rotation or passphrase change between the database copy and the key read** (the sealed root chosen by hash among `root.key.age` and `root.key.age.next`, the operational key chosen independently) restores to a consistent set; archive names are normalised; **per state:** a B0, B1, B2 and B3 backup each contain exactly the files of the table in section 13 (B1: plain `identity.key`, no `op.key`; B2: `root.key.age`, no `op.key`; B3: `root.key.age` and `op.key`; B0: none), the manifest records the state, and a B1 copy whose plain file was sealed between the copy and the read is retried and then fails with the message when no file is found.

**Restore.** Phase separation: the archive and manifest are byte-identical after phase 1, the install plan carries the new hashes of transformed files (a migrated database), a transformed file is installed although its hash differs from the manifest, a file damaged between phase 2 and the install is caught by the plan, SQLite is checkpointed and closed (no `-wal` or `-shm`); a missing or non-matching root file is rejected; **per state:** a B0, B1, B2 and B3 archive each restore and validate without files that their state does not have (a B1 archive restores without `op.key` and without a certificate, and an archive with files that do not fit its state is refused); **root rollback:** a backup made before a master-key rotation is restored while a test Worker holds the new pin: the Worker refuses the retired root (`ErrPinMismatch`), a serial floor does not help, the restore prints the rollback warning, a post-rotation backup restores the working state, and the out-of-band path (`minion worker reset` and a new invitation) re-enrolls the Worker; a restore issues no certificate and asks for no passphrase; a restored Hub opens its sealed root with the passphrase of the backup's time (after a change, the old one); **format-1 (0.6.x) archives** (cf. released `backup_test.go`, near lines 231-245 and 452-469): one with no recorded Hub identity and no key file restores as B0; one with a recorded identity and a matching plaintext `identity.key` restores and migrates to B1; one with a recorded identity and no key file is rejected with today's error; the OIDC secret round trip still decrypts.

**Activation fence.** Stalled handshake interleaving (takes its pair and generation, stalls, re-issue completes and closes sessions, the handshake resumes: registration fails, no session survives with the old signer); a handshake registered before the swap is closed by it; the generation rises on first issuance, re-issue and rotation and not on a passphrase change.

**Handshake and expiry.** Frame order and presence for the three modes, certificate bound into the transcript (one flipped certificate byte breaks every later step); the Worker never sends `sig_worker` before `sig_hub` verified, never reveals the invitation secret before step 7, never writes a pin before its commit point; each reason of the table, earliest wins (expired plus too low reports `cert_expired`; bad `sig_hub` plus too low reports `hub_sig_invalid`); window boundaries (`not_before - 1 h` accepted, one millisecond less refused, `now == not_after` accepted and admits nothing, one millisecond more refused, integer extremes); root transitions in the N2 order (chain, candidate, certificate under candidate, serial scope, `sig_hub`, atomic commit before any operation; a `hub_pub` different from `cert.root_pub` refused; a certificate under the old root with a new `hub_pub` refused; a rejected candidate leaves `max_serial` untouched); wrong root in each mode; a malicious Hub that never disconnects is cut at the deadline; wall time past `not_after` while the monotonic clock barely moved; wall clock backwards; monotonic equality counts as expired; an operation decoded before the deadline and admitted after it is not admitted; a revoke at or after the deadline is not applied and the pairing stays; a started write completes and is reported `unknown` while a read fails with `connection_lost`; `hub_cert_expired` before the upgrade; the Hub closes sessions at `not_after`.

**Pairing recovery.** Idempotency per (code, key): (1) lost welcome, then restart or retry by the same Worker with the same code within the lifetime and a fresh CPace, owner re-enters the code: the existing enrollment is returned, no second Worker, no new suffix, one `worker.pair_resume` audit event, the Worker commits; (2) crash after a valid welcome and before the commit, same result, and the `pair_resume` record (code, pairing id, expiry, root, serial, certificate hash) is durable before `sig_worker` was sent (error injection on the record write: no `sig_worker`); (3) Hub crash before its commit: no commit row, normal claim; (4) a different Worker key with the same code: today's refusal; (5) the same key with a different code and no repair window: `already_paired`; (6) a different user typing the code during resume: refused; (7) resume after code expiry: refused; (8) five wrong codes during resume close the resume; (9) a removed Worker during resume: `revoked`; (10) the Worker keeps a code only after the Hub's confirmation and `sig_hub` verified, and still retires it after an unauthenticated failure; (11) **identity substitution:** a resume answered by a Hub with a different root (even one that knows the code and passes CPace) is refused before `sig_worker`, the record and code are kept, and nothing is pinned; (12) a resume with a higher serial under the same root is accepted and the ratchet is raised at the commit, a lower serial or an equal serial with another hash is refused with the logged command; (13) `minion worker reset` and expiry delete the record and a new code is shown; (14) the `connect` mode ignores the record; the enrollment is uncommitted until `welcome`. **Owner re-issue:** only for a Worker with empty `first_connected_at` (not for a backfilled or connected one), only for its owner or an administrator, window of 10 minutes, completion with a new code keeps id, name and approval state, the window cannot be used by another key, expiry of the window restores `already_paired`; the Worker page shows the button only in the eligible state; **live row and tombstone:** a removed Worker (live row deleted, tombstone written) is not eligible and the conditional update changes zero rows, with no `tombstoned` column anywhere; **atomicity:** a first connect handshake racing the `repair_until` write and the repair completion is serialised by the conditional updates (exactly one of them wins, never both). Existing pairing tests keep passing.

**Retirement ratchet (12.5).** `Add` stores `max_serial` and `cert_sha256` in the version-2 metadata before `Wipe` (injected failure of the write aborts before the wipe); **a stale operational certificate (serial below the carried `max_serial`) cannot answer `not_enrolled`**: the entry stays pending and the Worker logs the refusal; a certificate with an equal serial and another hash is refused; a valid higher serial advances the stored ratchet durably before the Worker acts (crash between the advance and the action keeps the advance); a failed advance keeps the entry; a version-1 file is seeded by its first validated connection, cannot be retired by `not_enrolled` on that connection, and is retired by a later one; the migration rewrites it as version 2; a root transition during retirement resets the scope as in section 6.

**Revoke.** Live revoke, tombstone revoke at reconnect and self-retirement across a re-issue; a revoke signed by the root, by the previous operational key or by another connection's key is ignored and deletes nothing; a Worker is removed and its revoke verifies without any passphrase; a removed Worker that was offline across a re-issue is revoked at its next connect; an offline Worker passes a master-key rotation without re-pairing (its sessions were closed by the rotation); a pending Worker is revoked live and by tombstone.

**Migration.** A 0.6.2 data directory (with and without `identity.key.next`) starts in B1, serves no Worker, keeps its fingerprint and `mnk_` invitations after the passphrase is set and gets a first certificate with a fresh key; a crash at each step of section 14 is repaired by the next start; the banner for the recommended rotation shows while `migrated_from_06 = 1` and ends with the rotation; a 0.6.2 Worker state (pin, no `max_serial`) connects after both sides upgrade without re-enrollment and follows the rotation; a 2.0 Worker is refused with `proto_incompatible` and keeps retrying; an existing-database fixture for both forward migrations; existing Workers have `first_connected_at` backfilled.

## 18. Open questions

1. **Worker clock requirement.** A Worker with no real-time clock or a clock more than one hour behind `not_before` cannot connect. Is the one-hour tolerance right, and should the log line offer the exact clock difference (it does in this design) or an operator override?
2. **Default validity and warning window.** 180 days with warnings from 30 days means one session recycle per Worker about every 150 days. Would the owner prefer a longer default (up to the 400-day cap) given that renewal needs the passphrase by hand, or a longer warning period?
3. **Upgrade path from 0.6.2.** The 0.6.2 updater has an unwired protocol guard (section 14). Is a documentation-only caveat enough, or should a 0.6.x patch release wire the guard and teach `minion update` to accept a declared major step?
4. **Eligibility for Re-issue pairing.** The backfill makes every pre-0.7 Worker ineligible, including one that was genuinely stuck at upgrade. Acceptable, given such a Worker can be removed and enrolled again?
5. **Pairing review.** The independent cryptographic review of the CPace handshake is still pending; this design changes what CPace authenticates (the certificate is in its session id). Should the review be scheduled before the 0.7.0 tag?
6. **Passphrase policy.** Is a minimum of 14 characters with work factor 18 the right balance (an attacker with a stolen file gets one guess per second per core-equivalent of 256 MiB), or should the work factor be raised to 20 on Hubs with enough memory?
7. **Lockout denial of service.** Chosen in this revision (design decision): the local command has its own counter and lock, so the owner at the Hub host is never blocked by a web lockout; a repeatedly re-authenticated administrator who lacks the passphrase can still keep the web scope locked (section 10.6). Is that residual denial acceptable for the web scope?
8. **Optional expiry notifications.** Should the Hub send the 30-day warning outside the UI (for example by the existing notification channels), given that an unattended Hub otherwise stops serving at expiry?
