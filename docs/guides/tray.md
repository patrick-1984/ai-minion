# The tray app and its command line

Back to the [README](../../README.md).

The Minion tray app is a small menu in the system tray of Windows, a Linux desktop or macOS that shows the state of the Worker on this computer and lets you start, stop, pause and set it up without a terminal. The tray app itself ships in a later release; everything it does already works today from the command line, and this guide lists those commands.

The tray never talks to the Worker directly. Every menu item runs one `minion` command (or, for the tray's own settings, one `minion-tray` command) and reads the result from `minion worker status --json`. So every tray action also works in a script or a terminal, with the same result and the same exit status. `minion tray-actions --json` prints the table below as this `minion` knows it, and a test keeps the table, the tray menu and this guide equal.

## What the tray does and does not do

- **One Worker profile.** The tray works on one state directory and passes it as `--state-dir` to every command that takes it. A Worker of this user that runs on another state directory is shown as such ("A Worker runs with state dir …") and is never stopped, restarted or changed by mistake: `minion worker stop --state-dir D` and `minion worker restart --state-dir D` exit 27 when the running Worker uses another directory.
- **Status comes from `minion worker status --json` only.** The Hub key line, the MISMATCH warning, the pairing code and every enabled or disabled item are read from it. The tray shows the Hub key words the same way the CLI prints its `Hub key: …` line; a MISMATCH is the Worker's own check, not a comparison by the tray.
- **Secrets stay off the command line.** A join token goes to `minion worker join --token-file -` on standard input. The pairing code is shown in a menu item, never in a dialog or an argument. The tray never logs the output of the commands it runs.
- **Sessions that would end are always named first.** Stopping, restarting, joining and leaving can end sessions that live inside the Worker (Windows ConPTY sessions). The command refuses first with the number (exit 23) or because it cannot count them (exit 29). The tray then asks "N sessions will end" or "an unknown number of sessions will end" and only after a yes repeats the command with `--accept-loss N` or `--accept-unknown-loss`.
- **Elevation is a closed set of two commands.** On Windows, when starting or stopping the Worker service needs an administrator (exit 21), the tray asks Windows for elevation of exactly `minion worker start --json` (E1) or `minion worker stop --scm-only --accept-unknown-loss --json` (E2), run from the registered service binary only. It never elevates anything else: no restart, join, leave, update or set up. On Linux it shows the `sudo` command instead.
- **Set up stays in a terminal.** "Set up the Worker…" opens a terminal with `minion worker up`, which asks its questions there. The tray does not install anything itself.
- **No new power.** The tray grants nothing the command line does not: the Hub cannot lift a local block, and the tray does not open the Worker's control socket.
- **Block new sessions created through Minion** refuses `session_create` from every origin (the Hub, API keys, local commands, `mn`, MCP). Limit: a writable shared terminal can still start programs or sessions by typing. For a stronger switch use preview-only or share no sessions.

When a command refuses because sessions would end, the tray names the loss and, after a yes, runs the same command again with `--accept-loss {n}` (exit 23 named N sessions) or `--accept-unknown-loss` (exit 29: an unknown number of sessions will end).

For `hub.join` and `hub.pair` that run is not the same command again: the tray runs `hub.join.resume` and `restart` (see Retry), so that a consumed token or a changed sharing choice is never replayed.

The only commands a Windows tray runs elevated, on the registered service binary only:

- E1: `minion worker start --json`
- E2: `minion worker stop --scm-only --accept-unknown-loss --json`

Placeholders:

- `{attempt}`: pairing.attempt of the status
- `{epoch}`: enrollment_epoch of the status
- `{fp}`: worker_fingerprint of the status (may be empty)
- `{hub_fp}`: the Hub fingerprint (six words) entered in a dialog
- `{n}`: sessions_lost of the refusal (exit 23)
- `{revision}`: the revision of the minion worker share list --json response that the sessions (or the user's click) were read from
- `{session}`: the session name of the menu item
- `{sessions}`: the names to share, taken from the SAME minion worker share list --json response as {revision} (never from status), zero or more arguments; always placed after a literal -- so that a session named like an option stays a name
- `{share}`: all, none or later, chosen in a dialog
- `{state_dir}`: profile.state_dir of the tray's profile (C7)
- `{url}`: the Hub address entered in a dialog

## Exit statuses the tray reacts to

| Exit | Meaning | What the tray does |
| --- | --- | --- |
| 0 | done | shows the new state from `minion worker status --json` |
| 20 | the running Worker is too old for this command | disables the item and names the update |
| 21 | needs an administrator | Windows: asks for elevation (start and stop only); Linux: shows the `sudo` command |
| 22 | saved, but not confirmed in force | shows the real state and its reason |
| 23 | sessions would end | asks "N sessions will end", then repeats with `--accept-loss N` |
| 24 | no Worker is running | offers Start |
| 25 | the Worker is paused | offers Resume |
| 26 | no Worker service is installed | offers Set up the Worker |
| 27 | something changed meanwhile (revision, Worker instance, enrollment, pairing attempt, state directory) | reads the status again and asks again |
| 28 | the stopped Worker's database has another schema | "Start the Worker (or use the same minion version), then retry" |
| 29 | sessions that would end cannot be counted | asks "an unknown number of sessions will end", then repeats with `--accept-unknown-loss` |
