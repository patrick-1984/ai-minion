# Usage and subscription limits

Back to the [README](../../README.md).

Open **Usage** in the Hub for subscription limits, accounts, session counters, Worker inventory and personal token buckets. A user sees their own registered Workers. Administrators can see domain telemetry. Each person's account labels, ordering and buckets stay private. A subscription account is shown with its full login e-mail address (followed by a short digest that tells two workspaces of the same login apart): the Worker owner and Hub administrators see it unmasked, nobody else does.

**Workers** shows whether a Worker is online, when it reported and which harnesses it can identify. Select **Scan installed harnesses** to check a registered Worker. Some fields depend on a configured native producer; **Unknown** means no usable observation. The Hub does not infer tokens, charges or remaining capacity from a terminal screen.

**Claude Code data needs the Minion exporter.** Minion adds its status-line exporter to Claude Code settings so token, cost and limit data are reported; your existing status line keeps working. Once usage monitoring is accepted on a Worker, the Worker installs the exporter itself in the Claude profiles it knows (`~/.claude` and `CLAUDE_CONFIG_DIR`) at start and every ten minutes, with the same safe install as `minion worker config usage integrate claude` (it keeps the previous status line, refuses settings it cannot keep, and never touches a profile under managed settings). To opt out, set `usage_claude_exporter` to `off` (`minion worker config set usage_claude_exporter off`); the default is `auto`. To take it out of a profile again, run `minion worker config usage integrate claude --remove` (add `--claude-config-dir` for another profile): it deletes the Minion hooks, puts your previous status line back and deletes the manifest, and running it twice is harmless. The Worker adds the exporter again while the setting is `auto`, so also run `minion worker config set usage_claude_exporter off` to keep it removed. New Claude Code sessions report at once; restart running ones. **Workers** shows the exporter state of each Worker (installed, off, overridden by managed settings or disabled hooks, conflict) with the fix, and the command to run by hand as a fallback. **Sessions** points to it for a Claude Code session without tokens, and **Accounts** repeats it when no Worker has it. Claude Code re-runs its status line every few seconds in every session, idle ones too, with the limits of that session's last API response, so a subscription account's **Last checked** is the time its limits came from: an idle session that only repeats them does not make them newer. The limits of every session and every Worker that report the same account are merged per window: the later reset wins, and within the same reset the higher used share, because use within a window only grows; a window one report lacks is kept from another. A subscription account turns stale 15 minutes after the last API activity of its sessions; the card says since when. A Claude run that ends (its `SessionEnd` hook) is shown as stopped even while its tmux session stays open. Codex account limits work without an exporter; Codex session tokens are not collected yet.

**Codex turn activity.** On Linux, macOS and Android, after you accept usage monitoring, the Worker can add lifecycle hooks to your local Codex profile (`CODEX_HOME` or `~/.codex`) when Codex CLI 0.171.0 or later is on its path. In Codex, open `/hooks` to review and trust the Minion commands. The hooks report session and turn timing from local, bound tmux panes. To disable recording and automatic installation, run `minion worker config set usage_codex_exporter off`. You can also disable the commands individually in `/hooks`.

**Session activity.** On a shared tmux session the Worker can report Claude Code turns, permission requests, subagents, open planning tasks, and the running shell and workflow inventory attached to Stop hooks. The Hub shows the source and last lifecycle event time. The status-line callback supplies a heartbeat. After 15 minutes of silence, or 30 minutes without fresh evidence for a state, the Worker uses its screen detector. Hook metadata has no effect on input permissions. An untrusted, disabled, or absent integration leaves screen detection available. Set `usage_claude_exporter` to `off` to stop new Claude activity observations.

**Harness and access of a session.** The Worker finds a harness that a wrapper started (for example `bash -c 'claude ...; exec bash'`) from the process tree of the pane. It reads how the session signs in from the environment of the agent process itself, never of a wrapper shell, and only when that process runs as the same user as the Worker (Linux only; the user check and the read use the same open process, and a process that cannot be identified with certainty counts as **Unknown**). The Worker checks whether the key variables and the endpoint variable are set; it uses no key, token, host or URL value and sends only the access kind (API key, custom endpoint or subscription sign-in): access kind only, never an endpoint host. A session whose environment cannot be read (for example on macOS and Windows, where only the settings files are checked) shows **Unknown**. API key and custom endpoint sessions appear under **Accounts**, grouped by provider and access kind (**API keys (not told apart)**, **Custom endpoint (not told apart)**), without subscription limits, and stay out of the subscription overview. A session that Claude Code's own exporter saw using an API key stays an API session after the process ends.

Session lists order names naturally: `wb-2` comes before `wb-10`.

**Subscriptions** uses fresh observations from distinct subscription accounts. API-key usage is excluded from subscription capacity. An API-key or custom-endpoint account on **Accounts** shows the token and cost totals of its sessions twice: **Running now** sums only the sessions that are still running, and **History · last 90 days** sums the sessions that **Sessions** lists, running and ended in the last 90 days (not current spend). At **Accounts**, see each allowance's scope, consumed share, reset, observation time and source. A five-hour window and a weekly window are separate. Some plans have no five-hour limit: **No 5-hour window reported** appears only when the account's recent active reports have none (a capped plan whose 5-hour window is not open yet looks the same, so this is not a plan statement); when only idle or old reports lack it, the card says the 5-hour limit is unknown. A passive collector shows where its limits come from and when they last arrived (for example **Passive · from Claude status line**); it shows **Waiting for native observations** only when nothing arrived in the last 15 minutes. A pace label compares use against the elapsed part of a known window. Choose a collector Worker or a passive native session. The dedicated Codex reader does not start a conversation. Claude and Gemini native quota observations can become stale while a session is idle.

**Sessions** shows disclosed metadata, including start/end observations, folder, harness, model and available counters. **History** contains cumulative snapshots. Diagnostic events carry lifecycle types and timestamps. Prompts, task descriptions, commands, tool payloads and console output are outside the Usage report.

**Token buckets** organize either sessions or provider identities. Select individual members, all members on a Worker or all accessible members. A member can move to one bucket at a time within its kind or remain unassigned. This affects your view only.

## Show usage on your Workers (nominations)

A token bucket is private to you. **Nominating** a bucket publishes it: the bucket's label and its aggregate meters (percent, remaining amounts, resets, pace, coverage) leave the Hub and are copied to Workers, where other programs on that machine can draw a progress bar ([integrate with local programs](integrate-local.md)).

- **User nomination:** each user nominates at most one session bucket and one provider bucket of their own. They are shown on every approved Worker that user owns.
- **Domain nomination:** an administrator nominates one session bucket and one provider bucket for the whole Hub, from the administrator's own buckets. They are shown on every approved Worker. Administrators share these two slots: the last authorized change wins, and the admin list shows who set it.
- A Worker therefore receives up to four slots: `domain.session`, `domain.provider`, `user.session` and `user.provider`. Personal always means the Worker's Hub owner, also on an infrastructure Worker. A Worker that is still waiting for approval receives nothing.
- **Consent to include your observations:** one switch ("Your publication consent" on the Hub page) decides whether buckets that other people publish may include observations of your own sessions and accounts. It covers both audiences: other owners' personal nominations to their own Workers, and an administrator's domain nomination to every approved Worker of the Hub, including Workers of other people; a one-source bucket then reveals that you are the only source. Its text names both, and on a root Worker every local account of that machine can read the published copy. It is off until you turn it on. When you publish, the Hub asks you to confirm before publishing, names the data, the receiving Workers and, for a root Worker, the fact that every local account of that machine can read its copy. Withdrawing a nomination, deleting the bucket or losing the right to the domain slot removes it from the Workers within about a minute.
- **What Workers receive:** only the deliberately published label and the aggregate meters. Never member ids, session names, folders, account labels, key hints or other users' Worker ids. A meter without a known value has no value: nothing is estimated, and tokens left are never inferred from a percentage or from tokens spent.
- A preview shows exactly what your Workers receive: the Hub page, the `usage_readback` operation and the Hub-connected MCP tool. It does not need any Worker to be online.
- Nominating does not need the monitoring consent of a Worker: it is Hub data sent to the Worker, not a report from it.
- **Delivery:** the Hub sends the document to a connected Worker as a control frame (`readback.apply`) that only the Hub link carries. The Worker acknowledges it after it has stored the document locally, so the Hub knows what is published. A frame that is not acknowledged is retried with a growing delay, and the Hub reconciles every Worker every 60 seconds, so a Worker that was offline or lost a frame catches up. A delivery is a 5 minute lease: a Worker whose Hub link stays down keeps the last document, which consumers must treat as stale by its `expires_at` and `generated_at`. A document is bound to the Worker's current Hub owner and enrollment: it is cleared when the Worker is revoked, reset or replaced, and when its owner changes. Read it from another program with `minion worker discover --json --usage` or `minion worker status --json` (optional `usage` field).

## Register a Worker

An explicit enrollment option, `minion worker up --accept-usage`, accepts monitoring of all sessions on the selected Worker, including unshared sessions. A Worker may also review the pinned enrollment locally with `minion worker config usage` and accept with `minion worker config usage --accept`. New metadata-capable enrollments on a supporting Hub require this step before serving. Console sharing remains independently controlled. An update from a fully enrolled older Worker preserves its prior console permissions and shows pending or unknown statistics until acceptance.

Native source setup, provider translations, credential fingerprints, collector behavior, polling limits and the public API schema are documented in the [usage source reference](../../research/minion-usage/native-sources.md). See [Claude native integration](../../research/minion-usage/claude-integration.md) to configure Claude Code without replacing existing status-line behavior.
